# Marketing screenshots

The homepage images that show PLVS are rendered, not captured: the app's own React panels, fed by
committed fixtures that the production meter pipeline measured offline, drawn in headless
Chromium. The same command reproduces the same pixels on any supported machine; no audio device,
display scaling or idle machine is involved. The homepage and README share
`website/assets/landing-hero.webp`.

What the images are: real PLVS panels and real measurements of real audio, at a fixed moment.
What they are not: screenshots of a running app. Window chrome, OS fonts and LIVE scheduling are
outside them. The rendered images replace the earlier rule that the hero must come from the
Windows app. Native screenshots can be reviewed separately when needed; the retired capture
scripts are not part of the image generation or publication workflow.

## Files maintained in Git

- `assets/marketing/audio/full-band-crescendo/`: the
  `full-band-crescendo.source.json` (hashes of the Suno song, every stem and the arranged stereo
  bed, and the arrangement) and `ATTRIBUTION.txt`. The music was generated by SounDoer with Suno on a paid
  subscription and is owned by SounDoer, separately from the PLVS software licence. The beds are an
  arrangement of the song's stems (instruments entering in groups), not its master.
- `src/transfer/fixtures/homepageStereoV1.json` and `homepageMultichannel714V1.json` with their
  `.js` wrappers: what the meter pipeline measured. Never hand-edit them.
- `scripts/marketing/recipes/homepage-images.json`: every image's scene, fixture, Preset layout and
  controls, Loudness Profile, Interface Size, Snapshot offset, crop, published size and
  publication target.
- `scripts/marketing/render-homepage-images.mjs`, `homepage-render-lib.mjs` and
  `publish-homepage-images.mjs`: render, validate and publish. `homepage-preview.html` with
  `src/homepage-preview/main.jsx` is the renderer entry; it is not part of the app build.
- `website/assets/raw/landing-hero.png`, `landing-dock.png`, `landing-dock-custom.png` and their
  `.json`: the published originals and provenance of the images the site shows directly.
- `website/assets/raw/homepage-rendered/`: the feature originals (History, Frequency full and
  detail, multichannel, rules editor) and `provenance.json`; `prepare-homepage-assets.mjs` encodes
  them into `website/assets/homepage/` beside the Sharesets tiles.

`website/assets/raw/` stays in Git but is not published. `npm run website:check` fails when the
assembled site contains an image that no page, stylesheet or script names; when an image leaves the
website, delete its export and its original together. Runs, comparisons and reports stay under
ignored `artifacts/marketing/`.

## Render and review

```sh
node scripts/marketing/render-homepage-images.mjs
```

The command validates the recipe first: published sizes and crops, the Snapshot offset rule (a
Snapshot away from the final frame may not show Level Meter, Stats, Vectorscope, Correlation or
Stereo Map, whose readings exist only for that frame), and the hero's required Stats verdicts
(Integrated warn, Short-term warn, True Peak fail against the starter Profile), computed from the
fixture. It then renders every image at device scale 1.25 and writes the PNGs, `report.json` and
`comparison.html` into a new `artifacts/marketing/homepage-render-*` directory. `--only a,b`
renders a subset for iteration; a publishable run renders them all.

Open `comparison.html`: each rendered image sits beside the published one. Review composition and
readability. A rendered run is deterministic, so an unexpected difference after a code change is a
rendering change worth understanding, not noise.

## Publish

Commit everything first; a run from a worktree with changes is refused. Then:

```sh
node scripts/marketing/publish-homepage-images.mjs artifacts/marketing/homepage-render-TIMESTAMP
```

It refuses a run with another recipe, page errors, a wrong size, a PNG changed after rendering, or a
published original changed since the run. It writes the hero and Dock PNGs with lossless WebP
(decoded pixels must equal the PNG) and provenance, writes the feature originals and
`provenance.json`, and runs `prepare-homepage-assets.mjs`. Published sizes are fixed by the
recipe, so `website/index.html` keeps its `width` and `height`. Then:

```sh
npm run website:verify
```

and, with `npm run website:dev` running in another terminal,
`node scripts/marketing/review-dock-pair.mjs`, plus a look at the homepage at 1440, 820 and
390 px. Keep the originals, exports and provenance together in one commit.

## Change the music or the fixtures

No audio is stored in Git. The song and its stems live in the owner's
audio archive at `smb://QNAP00._smb._tcp.local/xichen/PLVS/PLVS_Audio_Archive`,
with stems under `full-band-crescendo/stems/` and a README naming each file.
`full-band-crescendo.source.json` pins the song, stems and arranged bed by SHA-256. With the archive:

```sh
npm run homepage:fixture -- --archive /Volumes/xichen/PLVS/PLVS_Audio_Archive
npm run sharesets:fixture -- --archive /Volumes/xichen/PLVS/PLVS_Audio_Archive
```

These examples assume the NAS's `xichen` share is mounted at `/Volumes/xichen` on macOS.
On other machines, pass the local mount path or a restored copy of `PLVS_Audio_Archive`, not
the SMB URL. The directory and its README were checked on 2026-10-31; this location check did
not verify every audio file's checksum. The separate promo production archive is documented in
[Video production](promo-video.md#maintainers-production-archive).

`PLVS_AUDIO_ARCHIVE` can stand in for `--archive`. Without `--write` they only check that the
committed fixtures match; with it they regenerate them. Both commands mix every bed in memory from
the stems: the stereo bed is refused unless its 24-bit WAV bytes match `arranged.sha256` in the
source JSON, so after an intentional change to the arrangement, pan positions or master, update
that hash from the error message. The Sharesets fixtures share the stereo bed and the arrangement,
so a music change refreshes the Sharesets previews too (`docs/website-and-sharesets.md`). Without
the archive the music fixtures are reported as source unavailable; `sharesets:fixture` still
checks its dialogue fixtures. The arrangement, the 7.1.4 and 5.1 placements, the stereo pan
positions and the stereo master settings (including its side gain) live in
`scripts/marketing/music-beds.mjs`. When the hero verdicts no longer hold after a change, adjust
the arrangement or master there; never edit a fixture.

## Historical capture audio

The NAS audio archive also retains `discovery/discovery-hero.wav` (Discovery by Scott Buckley,
CC BY 4.0), used by the retired real-app homepage capture workflow. Its provenance and credit
remain in `assets/marketing/audio/discovery-hero.source.json` and `ATTRIBUTION.txt` for archive
identification and attribution. It is not an input to the current homepage or Sharesets images.
The WAV remains outside Git; removing it from the current tree does not remove it from Git history.
