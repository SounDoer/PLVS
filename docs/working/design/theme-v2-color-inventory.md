# Theme V2 Color Inventory

**Date:** 2026-08-19  
**Status:** Static audit complete; runtime diagnostic pass pending  
**Design source:** `docs/superpowers/specs/2026-08-19-theme-v2-design.md`

## Purpose

This inventory records every intentional visible color family found in the current PLVS source and
classifies how Theme V2 should own it. It is evidence for the final Role Registry and implementation
plan; it is not itself the final persisted schema.

The audit distinguishes:

- **Core** — direct author intent on the Core page;
- **Palette** — direct author intent in Status, Intensity, or Frequency;
- **Linked** — follows another registered role while retaining its own semantic identity;
- **Auto** — generated by a compiler recipe and eligible for a meaningful Advanced override;
- **Internal Effect** — generated color/opacity with no first-release direct control;
- **Safety Fallback** — unreachable in a structurally complete resolved theme;
- **Asset** — scheme-selected or fixed image resource outside the color compiler.

## Audit method and limits

The static pass covered:

- all current authoring fields in `src/theme`;
- all CSS-variable publication in `src/preferences/applyDocumentTheme.js`;
- Tailwind semantic color utilities and direct CSS variables throughout `src`;
- SVG paint attributes and Canvas `fillStyle`, `strokeStyle`, gradients, and LUT consumers;
- Dock and accessory WebViews;
- Glass and tray consumers in frontend and Rust;
- hardcoded Hex, RGB, OKLCH, black/white, and raw Tailwind palette classes;
- declared tokens with no production consumer.

Generated first-paint CSS was inspected as compiler output, not as an editable source. Test fixture
colors were excluded unless they revealed a production contract.

The static pass cannot prove that every conditional visual state was actually rendered. A runtime
pass with a fluorescent diagnostic theme remains required before the registry is frozen. The final
section lists that pass explicitly.

## Current pipeline

```text
Builtin or Custom V1 Theme
├─ semantic: 24 shadcn fields
├─ seeds: accent, accentSecondary, good, warn, bad
├─ colormap: spectrogram stops
└─ colorScheme
            ↓
applyShadcnSemanticTokensToDocument + buildThemeTokens
            ↓
CSS variables
├─ DOM/Tailwind
├─ SVG
└─ Canvas reads through getComputedStyle

Separately:
├─ Spectrogram reads the theme object to build a LUT
├─ Glass receives colorScheme === "dark"
└─ Tray selects a light/dark image asset from colorScheme
```

The current system has no complete resolved-theme object. CSS variables are both publication output
and an indirect data API for Canvas. Spectrogram bypasses that API and looks up the theme object by
ID.

## Status and critical semantics

The current code has two overlapping critical sources:

- shadcn `--destructive` for destructive controls and validation text;
- `--ui-signal-bad` for measurement failure, capture errors, transport errors, and profile rules.

Theme V2 should use the Status Palette's Critical anchor as their common intent while retaining
distinct leaf roles when their presentation needs to differ:

| Visible role           | Current consumers                                                          | V2 classification                               |
| ---------------------- | -------------------------------------------------------------------------- | ----------------------------------------------- |
| Good status            | Correlation, Stereo Map, level bars                                        | Palette: Good                                   |
| Warning status         | Notices, profile rules, correlation, Stereo Map, level bars                | Palette: Warning                                |
| Critical status        | Destructive UI, errors, profile failure, clipping, correlation, Stereo Map | Palette: Critical                               |
| Content on Critical    | Destructive Button/Badge text and icons                                    | Auto from Critical plus target surface          |
| Status tint background | Status pills and transport clusters                                        | Internal Effect from Status anchor plus opacity |
| Status border/glow     | Status pills and transport clusters                                        | Internal Effect from Status anchor plus opacity |

Numeric thresholds such as correlation `< 0`, warning `< 0.35`, clipping level, or loudness-profile
rules remain measurement/product configuration. Only their resulting paint is theme data.

## Dead, misleading, or conflicting current contracts

1. **`--chart-1` through `--chart-5` have no production consumer.** They are defined, generated,
   and exposed by Tailwind but no component uses them. Theme V2 should remove them unless a concrete
   consumer is introduced before migration.
2. **Semantic `primary` and `ring` values are overwritten by `seeds.accent`.** The current custom
   editor can present fields whose saved values do not control the final output. V2 has one
   Interface Accent source and explicit derived bindings.
3. **The audited baseline declared `--destructive-foreground` but destructive Button/Badge hardcoded
   white.** The preparatory bugfix corrected this bypass; V2 preserves Content on Critical as an
   explicit leaf role.
4. **`--ui-signal-peak-sample` has no production renderer.** `samplePeakLineColor()` also has no
   production caller. Confirm whether the intended marker still exists visually; otherwise remove
   both rather than migrating a zombie role.
5. **Badge success/warning/danger variants have no production caller.** Their raw Tailwind colors
   should not become V2 roles solely because dead code declares them.
6. **`mutedForeground` carries too many meanings.** Secondary UI text, axes, units, hints, disabled
   content, and 3D plot ink currently collapse into one token plus local opacity.
7. **`destructive` and `signal.bad` duplicate critical intent.** They currently can diverge in a
   custom theme even though users reasonably perceive both as Critical.
8. **Stereo Map borrows Spectrum geometry tokens.** This is not a color leak, but the registry must
   avoid implying that shared opacity/stroke settings create shared color identity.
9. **Canvas fallback palettes disagree with current builtin anchors in places.** They are emergency
   constants, not reliable theme defaults, and should be centralized and made unreachable.

## Migration implications

- Map V1 `semantic.background`, a representative content surface, and `semantic.foreground` to
  Workspace, Surface, and Text.
- Map the old Accent seed to both Interface Accent and Primary Data to preserve current appearance;
  the two become independent after migration.
- Map Accent Secondary to Secondary Data and Signal seeds to the Status Palette.
- Map the old colormap directly into Intensity stops.
- Seed Frequency Low/Mid/High and associated roles from the V1 scheme-specific resolved output.
- Compare every V1 resolved leaf with V2 automatic output. Preserve differences as sparse Advanced
  overrides, including old semantic surface/text fields.
- Do not migrate unused `chart1–5`, dead Badge variants, or the unused sample-peak token as user
  intent unless runtime verification finds a real consumer.
- Preserve alpha-bearing V1 shell values through final rendered leaf overrides where necessary;
  do not reintroduce alpha into V2 Core colors.

## Runtime diagnostic pass

Before role IDs and the implementation plan are frozen:

1. Add a development/test-only diagnostic authoring theme with deliberately unrelated fluorescent
   Core, Status, Intensity, and Frequency colors.
2. Compile it through the proposed V2 path rather than hand-setting arbitrary component styles.
3. Traverse at least:
   - normal, hover, focus, active, selected, disabled, invalid, destructive, and modal states;
   - every Workspace panel and mode, including snapshot, selection, hold, persistence, Spectrogram
     2D/3D colorized/monochrome, Waveform frequency color, and Centroid;
   - Dock compact/standard/expanded modules and both accessory windows;
   - Glass on/off and System/Fixed transitions;
   - tray light/dark asset switching.
4. Record every visible color that does not follow the expected fluorescent family.
5. Either bind it to a registered role, classify it as an Internal Effect/Asset/Safety Fallback, or
   remove it as dead code.
6. Repeat the hardcoded-color scan with only an explicit allowlist remaining.

## Static-audit conclusions

- The six proposed Core Colors cover every current single-color source of user intent.
- Status, Intensity, and Frequency are the only true multi-color authoring groups found.
- Dock introduces no additional color semantics; it reuses interface, data, and status roles.
- Native code introduces no arbitrary theme color beyond `colorScheme` and scheme-selected assets.
- Current special cases are derivation/publication problems, not evidence for more Core Colors.
- The largest cleanup areas are overloaded muted text, duplicate Critical semantics, scheme-hardcoded
  Waveform colors, Canvas fallback parsing, surface effect literals, and dead shadcn chart slots.
- Static evidence supports the role-based design. The runtime diagnostic pass is the remaining proof
  against state-dependent omissions.
