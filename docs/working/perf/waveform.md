# Waveform 体检表

**状态：** 四维都已测，并且**已经在真实窗口里采过 profile**（两对受控采样，见 §2.6）。
D2 的颜色循环已优化（−27%，输出逐字节相同）；D3、D4 量过后判定不值得改；D1 正确性有覆盖、
成本未测。

**§2.6 推翻了本文档最初的两个判断，正文已就地更正**——旧的说法不再保留在上面，只在 §2.6 里
说明错在哪。

工具：`npm run benchmark:waveform-render`（新增）、`npm run benchmark:history`（已有）。
存储与 payload 的数字用一次性脚本量的，方法写在对应小节里。

## 0. 它跟别的 panel 不共用什么

Waveform 是目前查过的四个里**最独立**的一个：

| 维度   | 情况                                                                                                 |
| ------ | ---------------------------------------------------------------------------------------------------- |
| **D1** | 自己的 `WaveformAccumulator`（`src-tauri/src/engine/waveform_accumulator.rs`），纯 min/max，不碰 FFT |
| **D2** | 自己的 `drawWaveformCanvas`，**每个声道一张 canvas**                                                 |
| **D3** | 落在 `LoudnessHistorySlab` 的三列 + 自己的 `WaveformHistoryIndex`                                    |
| **D4** | 搭 `loudnessHistTick`（约 10.5/s）与 `visualHistTick`（25/s）的便车，没有自己的 key                  |

唯一的外部依赖是 Frequency Color 与 Centroid 用的谱线指标，来自 `visualWaveformHist`
（`dominantFrequencyHz` / `spectralCentroidHz` / `tonality`），那是 25 Hz 的视觉环。

**它没有 request key。** 所以 Spectrum 那一轮关于 key 数量、栅格重发、slab 分裂的结论
在这里一条都不适用，`AGENTS.md` 里"控件值进 key 就要花内存"的那条也管不到它。

## 1. D1 — Rust 计算

### 1.1 线程边界：合规

`waveform.push_interleaved` 在 `meter_pipeline.rs:735` 被调用，而 pipeline 跑在
`run_meter_pipeline_bridge_thread`——**从投递队列取 PCM 的桥接线程，不是音频回调线程**。
累加器里的 `history_sub_pairs.extend_from_slice` 会分配，这在回调线程上会违反
`AGENTS.md` 的 Boundaries；在这条线程上不会。**查过了，没问题**，记下来免得下次再查一遍。

### 1.2 正确性：有覆盖

| 测试                                                  | 钉住的东西                                       |
| ----------------------------------------------------- | ------------------------------------------------ |
| `captures_channel_extrema_without_the_meter_pipeline` | 交错 PCM → 每声道 min/max，以及 sub_pairs 的排布 |
| `sub_block_boundary_survives_multiple_pushes`         | 跨多次 push 的 256 样本边界，含尾部不满的那块    |
| `history_and_visual_windows_reset_independently`      | 两个窗口各自复位——它们由不同的节奏驱动           |

谱线一侧（`dsp/spectral_waveform.rs`）另有三个：纯音、静音、宽带。

### 1.3 sub-block 是**按样本数**定的，不是按时间

`SUBBLOCK_SAMPLES = 256` 写死。于是同一个常数在不同采样率下代表不同的时间分辨率，
而且**每行的字节数随采样率线性增长**：

| 采样率     | 一个 sub-block | 95 ms tick 的 sub-block 数 | 每行 subPairs（立体声） |
| ---------- | -------------- | -------------------------- | ----------------------- |
| 44.1 kHz   | 5.80 ms        | 17                         | 272 B                   |
| **48 kHz** | **5.33 ms**    | **18**                     | **288 B**               |
| 96 kHz     | 2.67 ms        | 36                         | 576 B                   |
| 192 kHz    | 1.33 ms        | 72                         | 1152 B                  |

**这不是 bug，但它是下面 D3 那个数字的隐含前提**：56.6 MiB 是 48 kHz 的答案，
192 kHz 下同一份历史要 4 倍。

### 1.4 副作用：48 kHz 下最大缩放时，画布比数据细

5.33 ms 的 sub-block 在 1200 px 宽的面板上、5 秒（缩放下限）窗口里，比一个像素（4.17 ms）**更粗**。
实测（`waveformMath.js` 的 carry-forward 补出来的重复列）：

|                 | 桶数     | 重复上一列的 |         |
| --------------- | -------- | ------------ | ------- |
| 600px / 5s      | 600      | 0            | 0%      |
| **1200px / 5s** | **1200** | **246**      | **21%** |

放大到头、面板又够宽的时候，**约五分之一的列是复制出来的**。600 px 宽下不会发生，
60 秒及以上的窗口不会发生。

这是一条分辨率结论，不是性能结论，而且它**反对**去压缩 subPairs 的存储——那 288 B/行
已经是勉强够用，不是有水分。

### 1.5 计算成本：**未测，且这一轮不该测**

累加器对每个样本做 6 次 min/max。48 kHz 立体声是每秒 96k 个样本、约 576k 次比较，
落在一条已经在跑 FFT 引擎的线程上。**没有证据说它是问题，也没有证据说它不是。**

要量它得给 `WaveformAccumulator` 加一个可从外部调用的入口——它现在是 `pub(super)`，
集成测试够不着。那是代码改动，按 `README.md` 的规矩不能混进调查轮。
标记为 `HYPOTHESIS`：**优先级低**，因为 D2 那条已经足够解释掉可观察到的成本。

## 2. D2 — 前端渲染

三段串在一起：切片 → 谱线对齐 → 绘制。**每一段的成本都要乘以声道数**，因为一个声道一张
canvas。下面所有数字都是**单条 lane**的。

条件：立体声、`HIST_EMIT_MS = 95` 的行、16 ms 帧预算。

### 2.0 先钉一件事：它不是每帧都画

`WaveformLane` 的绘制走 rAF 合并，`drawParamsRef` 的依赖只在切片结果和谱线指标变化时才变，
所以它画不到 62.5/s。

**实测 31.6 次/秒**（文件分析模式，2026-08-29）。方法是在 `CanvasRenderingContext2D.prototype`
上包一层计数，按 canvas 归属分开数；同一次采样里 Spectrogram 的 `putImageData` 是 31.8/s，
两者一致。

先前这里写的是"不超过 25/s"，是从依赖链推的，**推错了**。下面的每帧数字按 31.6/s 折算。

### 2.1 主结论：**Frequency Color 是逐桶发绘制命令的**

`drawWaveformCanvas` 的经典路径把整条包络攒成**一条** path，一次 `fill` 一次 `stroke`。
Frequency Color 路径不能这么做——每个桶的颜色都不同——于是它**每个桶各发一次**
`beginPath` / `fill` / `beginPath` / `stroke`。

实测的画布命令数（单 lane，一次绘制）：

|                                   | 桶数     | fill     | stroke   | beginPath | 样式写入 |
| --------------------------------- | -------- | -------- | -------- | --------- | -------- |
| 600px / 60s，经典                 | 601      | **1**    | **1**    | 1         | 5        |
| 600px / 60s，Frequency Color      | 601      | **601**  | **601**  | 1202      | 3005     |
| 1200px / 60s，经典                | 1200     | **1**    | **1**    | 1         | 5        |
| **1200px / 60s，Frequency Color** | **1200** | **1200** | **1200** | **2400**  | **6000** |

立体声下把这些乘二：**一次绘制 2400 次 fill + 2400 次 stroke + 12000 次样式写入**。

JavaScript 那一半的耗时（单 lane）：

|                  | 经典         | 经典 + Centroid | Frequency Color | + Centroid   |
| ---------------- | ------------ | --------------- | --------------- | ------------ |
| 600px / 5s       | 0.015 ms     | 0.039 ms        | 0.379 ms        | 0.391 ms     |
| 600px / 60s      | 0.007 ms     | 0.024 ms        | 0.344 ms        | 0.366 ms     |
| 600px / 7200s    | 0.005 ms     | 0.006 ms        | 0.130 ms        | 0.134 ms     |
| 1200px / 5s      | 0.014 ms     | 0.050 ms        | 0.561 ms        | 0.649 ms     |
| **1200px / 60s** | **0.014 ms** | 0.046 ms        | **0.652 ms**    | **0.686 ms** |
| 1200px / 7200s   | 0.008 ms     | 0.010 ms        | 0.266 ms        | 0.261 ms     |

1200px / 60s 立体声：经典 0.028 ms（0.2% 预算），Frequency Color **1.37 ms（8.6% 预算）**，
约 **49 倍**。

这个数字**只含 JavaScript 那一半**：绘制是拿一个记录用的桩 context 量的，循环、颜色计算、
调用开销都在里面，每次 `fill` / `stroke` 背后的原生栅格化不在（Node 里没有 canvas）。
最初这里写的是"真实差距只会更大"——**§2.6 的 profile 证明那是错的**：原生那一半几乎不要钱，
这个下界差不多就是全部。命令数仍然是结构事实，只是它贵在 JS 侧而不是浏览器侧。

Centroid 叠加是廉价的（+0.02~0.09 ms，一条 path），**不是问题**。

### 已落地：把颜色循环里的循环不变量提出去（−27%，输出逐字节相同）

成本拆开之后（`benchmark:waveform-render` 的 "Inside the Frequency Color loop"，1200 桶）：

|                             | 每次绘制     |
| --------------------------- | ------------ |
| 改前                        | 0.253 ms     |
| 只去掉字符串构建            | 0.158 ms     |
| **锚点外提 + 不再分配数组** | **0.096 ms** |
| 再去掉字符串构建            | 0.021 ms     |

两件事，都不改输出：三个锚点和它们的对数**只由两个 split 控件决定**，原本每个桶重算六次
（三次 `sqrt` 三次 `log`）；`mixRgb` 用 `.map()`，每个桶分配两个数组。现在
`waveformFrequencyScale` 每次绘制建一次，`waveformFrequencyRgbInto` 写进一个复用的数组。

整幅绘制的收益（1200px / 60s 单 lane）：**0.652 → 0.477 ms（−27%）**。比循环本身的 62%
小，因为画布几何那部分没动。

**凭什么说输出没变**：`spectralWaveformMath.test.js` 里放了一份改动前算法的**独立转写**，
在两组 split × 约 1.8 万种输入组合上逐字节对拍，边界（三个锚点各自 ±1e-9）、越界与 NaN 的
频率和 tonality 都在里面。中间那次舍入——插值出来的 hue 先取整，再和 neutral 混合——也必须
一致，这是最容易在"优化"时被抹掉的一步。

顺带修掉一个隐患：原来 `frequencyHz <= 0` 与命中首尾锚点时**直接把调色板数组返回出去**，
调用方改一个元素就会改掉主题。现在一律返回新数组，有测试钉住。

### 2.6 在真实窗口里采到的：原生那一半几乎不要钱（2026-08-29）

前面所有 D2 数字都是脱离应用测的，**原生栅格化量不到**。这一节把它补上。

**方法。** 远程会话没有音频设备，所以走文件分析（`README.md` 那条路）。用 Node 生成一段
10 分钟、48 kHz 立体声的素材（调频正弦 + 宽带噪声 + 慢包络，让主频和包络都真的在动），
`PLVS_BUILD_SOURCEMAP=1` 重建，从 CDP 驱动：切 FILE、emit `tauri://drag-drop`、开关
Frequency Color、采 10 秒。**同一次运行、同一份素材、只切一个开关**，各采两对。

|                             | 关        | 关（第二对） | 开           | 开（第二对） |
| --------------------------- | --------- | ------------ | ------------ | ------------ |
| `(program)`                 | 1591.2 ms | 1653.8 ms    | 1663.8 ms    | 1671.1 ms    |
| `drawWaveformCanvas` 自耗时 | 未进榜    | 未进榜       | **136.2 ms** | **144.3 ms** |

lane 宽 340 px；采样期间分析全程在跑，前后都验过百分比在推进。

**结论：`(program)` 开关前后没有区别。** 差 30~80 ms / 10 秒，落在两次"关"之间的自然波动里
（1591 vs 1654）。每秒 21600 次 fill+stroke 提交（两条 lane 合计）在这里量不出来——`fill` 和
`stroke` 连前 14 都进不去，而 Stereo Map 的 `addColorStop` 以 91 ms 进了榜。

**所以整个成本就是 JS 那一半：136~144 ms / 10 秒，约 1.4%。** benchmark 按 340px 折算预测
约 117 ms，实测 136~144，差 20% 以内——**脱离应用的那套测量是可信的**。

### 2.6.1 这一节推翻了什么

| 原判断                                | 实际             | 影响                                               |
| ------------------------------------- | ---------------- | -------------------------------------------------- |
| "JS 侧的数字是下界，真实差距只会更大" | 下界几乎就是全部 | **ImageData 重写不成立**——它换掉的正是免费的那部分 |
| "绘制不超过 25/s"                     | 31.6/s           | 折算比例改了                                       |

**为什么 ImageData 那条路被否掉**：它要付的代价是丢掉抗锯齿、丢掉 `fracPhase` 的亚像素滚动
（`waveformMath.test.js` 有专门用例钉着它）、外加重写画笔，换来的是一个量不出来的收益。

### 2.6.2 采样时踩的一个坑

第一次采"关"的那份，`(idle)` 是 69%——**因为分析已经跑完了，采的是空转的窗口**。这正是
`README.md` 里"空转的 profile 比没有更糟"那条。10 分钟的素材大约 65 秒跑完，而两次采样加上
中间的开关操作超过了这个时间。

改法是每次采样前重新触发一次分析，并在采样**前后各读一次进度百分比**确认它在推进。
上表的四份都过了这道检查。

### 2.2 合并成 run 只在放大时有用

Stereo Map 那一轮的修法（把颜色相同的连续段并成一次绘制）在这里的收益完全由缩放决定，
因为颜色来自 40 ms 的视觉环：**一个谱线行能覆盖几个桶**，就是 run 的长度上限。

|                | 每个谱线行对应的桶数 |
| -------------- | -------------------- |
| 1200px / 5s    | 9.60                 |
| 600px / 5s     | 4.80                 |
| 1200px / 60s   | 0.80                 |
| 600px / 60s    | 0.40                 |
| 1200px / 7200s | 0.01                 |

**默认的 60 秒窗口下桶比谱线行还少**，相邻桶天然拿到不同的行，run 长度就是 1，合并一无所获。
只有 5 秒那一档能到 10 倍。

这是算术，不是实测：真实素材里相邻的谱线行也可能给出相同颜色，那会让 run 更长。
但**上界是结构决定的**，而在最常用的那一档缩放上，上界就是 1。

**所以不要照抄 Stereo Map 的修法。** 这条路径要便宜下来，得换一种不按桶提交的画法
（例如把颜色写进 ImageData 自己栅格化，像 Spectrogram 那样），那是设计改动，不是局部优化。

### 2.3 切片：索引路径是对的，但有一个反转

`sliceWaveformSubHistory` 逐行扫，`sliceWaveformSubHistoryFromIndex` 在
一像素一行及更疏的时候查 `PowerOfTwoMinMaxIndex`。

**量的时候先踩了一个坑，记下来**：第一版 fixture 用普通数组喂切片，结果索引路径**比扫描还慢**。
原因是普通数组把行对象白送给切片，而应用里的 `histSourceList` 是 `LoudnessHistorySlab`——
每读一行要从打包的列里**实体化一个行对象**（含三次 `RaggedFloatColumn.at()` 分配）。
索引存在的意义正是跳过这件事。**拿数组量等于替应用作弊**，改成喂真 slab 之后：

|                    | 扫描（数组 fixture） | 扫描（真 slab）       | 走索引                         |
| ------------------ | -------------------- | --------------------- | ------------------------------ |
| 600px / 5s         | 0.045 ms             | 0.080 ms              | 不适用（放大到这一档不走索引） |
| 600px / 60s        | 0.030 ms             | 0.132 ms              | 0.231 ms                       |
| **600px / 7200s**  | 0.661 ms             | **3.676 ms（23.0%）** | **0.637 ms（4.0%）**           |
| 1200px / 5s        | 0.046 ms             | 0.050 ms              | 不适用                         |
| 1200px / 60s       | 0.150 ms             | 0.205 ms              | 不适用                         |
| **1200px / 7200s** | 0.703 ms             | **3.965 ms（24.8%）** | **1.144 ms（7.2%）**           |

两条结论：

1. **两小时窗口下索引省 3.5 倍**，把 25% 的帧预算压回 7%。它是有用的。
2. **60 秒 / 600px 那一档索引反而更贵**（0.231 vs 0.132 ms）。切换条件是
   `coordsPerBucket >= 1`，而这一档正好是 1.05——刚过门槛，桶几乎一行一个，
   查索引的固定开销还没被摊薄。绝对值只有 0.1 ms，**不值得为它加一条阈值**，
   但知道这个反转存在，免得以后看到"索引更慢"以为是 bug。

### 2.4 回退到扫描的那条路值多少

`hasNaNInRange` 命中就整段退回扫描。代价按上表：**两小时窗口下 0.64 ms → 3.7 ms**。
NaN 行是真实存在的（`waveformHistoryIndex.test.js` 有四个用例专门管它），
所以这不是理论风险，而是一个**已知的、有测试覆盖的、成本已量化的**降级。没有动它的理由。

### 2.5 谱线对齐：为读一个时间戳实体化整行

`sliceSpectralWaveformMetrics` 与 `getWaveformHistoryWindowBounds` 都在**用整行去读一个
`timestampMs`**，而 slab 上有现成的 `timestampAt(index)`——`valueAt` 的注释里就写着它是给
"hot paths that would otherwise materialise a whole row" 用的。

实测（1200 行）：

|                          | 每帧     |
| ------------------------ | -------- |
| `slab.at(i).timestampMs` | 0.106 ms |
| `slab.timestampAt(i)`    | 0.030 ms |

**当时的判定是"省 0.076 ms，太小，不值得单独做"——这个判定是错的**，因为它假设每帧读 1200 行。
真实次数由 §2.7 给出：等于整个环的长度。已随 §2.7 一并修掉。

## 2.7 D2 主发现：谱线对齐的成本随会话时长增长（2026-08-29，已修）

这一条是顺着 §2.6 profile 里两个"比画笔还大"的条目挖出来的，量级比这份文档里其他所有
D2 条目加起来都大。

### 机制

`sliceSpectralWaveformMetrics` 里 `rowIndex` 从 **0** 开始线性前进，找可见窗口的第一行。
而 `rows` 是 `intake.getVisualWaveformHist()`——**整个视觉环，不是窗口视图**，容量
`historyRetentionSec / 0.04`（默认 3600 s → 9 万行，最大 14400 s → 36 万行）。

于是窗口之前的每一行都被 `rowFrom` 完整实体化出来（一个对象 + 三个 `subarray`），
只为读一个 timestamp，然后丢掉。实测 `rowAt` 调用数 = **环行数 + 2400**。

### 代价，以及那个对照组

| 保留            | 环行数  | 改前（窗口在实时边缘） |         | 对照：窗口在最旧端 | 改后        |
| --------------- | ------- | ---------------------- | ------- | ------------------ | ----------- |
| 0.5 h           | 45,000  | 8.21 ms                | 51%     | 0.73 ms            | **0.32 ms** |
| **1 h（默认）** | 90,000  | **14.91 ms**           | **93%** | 0.65 ms            | **0.36 ms** |
| 2 h             | 180,000 | 29.33 ms               | 183%    | 0.66 ms            | **0.32 ms** |
| 4 h             | 360,000 | 59.45 ms               | 372%    | 0.66 ms            | **0.32 ms** |

**对照列是关键**：同一个环、同样 1200 个桶，只把窗口挪到最旧端让 seek 归零，成本立刻回到
0.65 ms 并且**不再随环长变化**。所以整条曲线全部来自那个 seek，不是别的地方。

读取次数 **92,399 → 3,915**，且四个档位一致（窗口内 1500 行 + 每桶 2 次 + seek 的 log₂）。
改后连对照组都跑赢了（0.65 → 0.32 ms），因为时间戳不再实体化整行——那就是 §2.5 那条。

### 两件让它更糟的事

**它是随运行时长恶化的。** 环要一小时才填满，所以刚启动完全正常，之后一路劣化到 93% 帧预算。
这大概就是它一直没被发现的原因。

**默认配置下这份结果没有人读。** `spectralMetrics` 只喂给 `drawWaveformCanvas`，而那里只在
`frequencyColor` 或 `centroid` 打开时才碰它，**两个开关默认都是关的**。
（这一条没有修，见 §2.7.3。）

Dock 的 waveform 模块（`DockWaveform.jsx:286`）调同一个函数，同样中招，同样修好。

### 2.7.1 修法

`seekRowAtOrBefore` 二分查找起始行，`timestampAt` 读时间戳不再实体化整行
（`timestampAtWaveformCoordinate` 的两处也一并换掉）。

**前提**：时间戳不递减。引擎发的是 `u64` 毫秒，`FrameIntake` 的会话边界偏移保证跨重启仍有序。
`appendRow` 会把任何非有限时间戳存成 `-Infinity`，这样一行夹在中间会破坏前提——但它在下面的
时效检查里本来就解析成"该桶无数据"，两种走法结果相同。这一点写在函数注释里。

### 2.7.2 测试怎么钉的

两条，都不依赖实现细节：

- **"窗口前面有多少历史都不改变答案"**——同一段可见数据，一次前面接 1 行、一次接 500 行、
  一次接 20000 行，输出必须逐元素相同。写这条时第一版红了，查出来是**我的 fixture 在按行序号
  生成数值**，同一时刻在两个环里序号不同；改成按时间戳生成才是我要问的问题。
- **读取次数上界**——9 万行的环，读取次数不得超过 `2·log₂(n) + 4·(窗口行数 + 像素数) + 16`，
  并且不得达到环长的四分之一。这条在修之前是红的（92399 vs 10850），是它先复现了这个 bug。

另有一条钉住等值时间戳与空隙的落点。

### 2.7.3 第三层：两个开关都关时根本不算（已落地）

`spectralMetrics` 的读者只有 `drawWaveformCanvas` 里的两处，一处在 `frequencyColor` 下、
一处在 `centroid` 下，**两个开关默认都是关的**。悬停与快照路径都不碰它（查过）。
所以默认状态下，面板每个视觉 tick 算出一份结果，然后整份丢掉。

现在 `spectralOverlaysOn` 为假时直接返回共享的 `EMPTY_SPECTRAL_WAVEFORM_METRICS`。
Dock 的模块用同一个闸门。

**省下多少，以及为什么这笔钱变小了。** §2.7 修完之后单次只要 0.32~0.36 ms，所以这一层省的是
**约 1% 的单核**（0.3 ms × 31.6/s）。更值钱的是分配：每次要新建每声道三个 `Float32Array`，
1200 像素宽立体声一次约 28.8 KB，按 31.6/s 就是**每秒约 900 KB 的垃圾**——profile 里 GC 占
2.2%~2.4%，这部分有它的份。

**如果先做这一层，§2.7 那个 bug 会被藏起来。** 默认配置下它不再运行，症状消失，而打开
Frequency Color 的人照样吃 93% 的帧预算。顺序是重要的：先修慢，再修白做。

`EMPTY_SPECTRAL_WAVEFORM_METRICS` 是冻结且共享的单例，所以它同时是一个**稳定的引用**——
停在这个状态的面板不会每次渲染都给 lane 递一个新对象、再排一次重画。

**三条风险各有一条测试**（`WaveformPanel.test.jsx`）：两个开关都关时**一次都不调用**；
任一开关打开时立刻调用；关掉之后**即使窗口移动了**也不再调用。

最后一条最初写得是假的：只 rerender 一次，memo 的其他输入没变，去掉闸门它照样绿。
补上"窗口也动一下"才让它真的在问问题。**三条都验过能红**——把闸门临时改成恒真，
第一条和第三条同时变红。

## 3. D3 — 历史存储

方法：用真实的 `LoudnessHistorySlab` 与 `WaveformHistoryIndex` 按 4 小时容量（144000 行）
灌满，量 `heapUsed + arrayBuffers` 的增量，`--expose-gc` 前后各强制回收一次。

|                                                    | 4 小时总量   | 每行    |
| -------------------------------------------------- | ------------ | ------- |
| `LoudnessHistorySlab`（含 loudness 的 m/st 两列）  | **48.2 MiB** | 351.2 B |
| 其中 `waveformSubPairs`                            | **39.6 MiB** | 288 B   |
| `WaveformHistoryIndex`（索引 + 原始行 + NaN 序列） | **8.4 MiB**  | 61.0 B  |
| **Waveform 相关合计**                              | **56.6 MiB** |         |

### 判定：没有水分，也不需要有

放在一起看：

|                   | 4 小时       |
| ----------------- | ------------ |
| Waveform 全部     | **56.6 MiB** |
| Spectrum 单 key   | 1.38 GB      |
| Stereo Map 单 key | 4.37 GB      |

**Waveform 占整个历史占用的约 1%。** 最大的一块 subPairs（39.6 MiB / 70%）就是
§1.4 里已经证明"勉强够用"的那份分辨率——1200px 最大缩放下已经有 21% 的列在复制邻居了，
再降就是可见的画质损失，换回来的是不到 1% 的内存。

**这一维不值得再投入。** 唯一要记的是 §1.3 的那条：**192 kHz 下这个数字是 4 倍**（约 226 MiB），
仍然不大，但别拿 56.6 MiB 当所有采样率的答案。

## 4. D4 — 传输

Waveform 没有自己的通道，它的字段挂在两个 tick 上。方法：按 Rust 的 f32 序列化规则
（ryu，能往返 f32 的最短十进制）拼出实际的 JSON 片段，量 UTF-8 字节数，乘节奏。

|                                     | 每次         | 节奏   | 带宽            |
| ----------------------------------- | ------------ | ------ | --------------- |
| `loudnessHistTick` 的 waveform 字段 | 925 B        | 10.5/s | **9.51 KiB/s**  |
| 其中 `waveformSubPairs`             | 810 B（88%） |        |                 |
| `visualHistTick` 的 waveform 字段   | 73 B         | 25/s   | **1.78 KiB/s**  |
| **合计**                            |              |        | **11.29 KiB/s** |

### 判定：不动

对照 Spectrum 那一轮：栅格移出每帧之后，单个 combined key 仍是 **2.58 MiB/s**。
**Waveform 全部的传输量是它的 0.4%。**

Spectrum 剩下的第 3 层（dB 数组改 f32 二进制）如果哪天做了，同一套机制自然会覆盖到
`waveformSubPairs`——810 B 的文本对应 288 B 的二进制。**但那是协议轮的事，不构成
为 Waveform 单独开一刀的理由。**
