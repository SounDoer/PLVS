# Spectrogram 体检表

**状态：** D1、D3、D4 继承自 Spectrum，无独立工作；D2 的 2D 路径已落地滚动复用；两种 3D mode
在真实 WebView2 中都已确认是热点，CPU 总账几乎相等（Surface 花在渲染进程，Lines 花在 GPU
进程），GPU 引擎上 Lines 约为 Surface 的 2.2 倍，两者都待决策。

## 0. 继承关系（先钉死，免得重做）

Spectrogram 不是一个独立的数据管线，它和 Spectrum 共用同一份东西：

| 维度 | 情况 |
| --- | --- |
| **D1 Rust 计算** | 完全继承。`SpectrogramPanel` 用的就是 `spectrumRequestKeyFromControls`，同一个 key、同一批 consumer、同一个 96 点/八度栅格。见 `spectrum.md` §1.5、§1.8 |
| **D3 历史存储** | 完全继承。它读的是 `getSpectrogramSnapsForKey(key)`，也就是 Spectrum 写进去的**同一块 `SpectrumHistorySlab`**。见 `spectrum.md` §3.0 |
| **D4 传输** | 完全继承。行、栅格、payload 都是 Spectrum 那条链路的。见 `spectrum.md` §3.5、§3.6 |
| **D2 前端渲染** | **唯一的独立面** —— 两条画布路径都是它自己的 |

所以这一轮实质上只有 D2。

## 1. D2 实测（2026-08-29）

工具：`npm run benchmark:spectrogram-render`。两条画笔都是对历史行的纯计算，可脱离应用测；
`putImageData` 的上传与画布合成仍在测量范围之外。

条件：958 频带、60 秒窗口（1500 行）、16 ms 帧预算。

| | 每帧 | 占预算 |
| --- | --- | --- |
| 600×300 整幅重绘 | 5.70 ms | **36%** |
| 600×300 只画新增一列 | 0.008 ms | 0.1% |
| 1200×600 整幅重绘 | 20.14 ms | **126%** |
| 1200×600 只画新增一列 | 0.016 ms | 0.1% |

### 主结论：**每帧重绘整幅图，而每帧只有一列是新的**

`paintSpectrogramImageData` 开头就是 `words.fill(0)`，然后把窗口内所有行重画一遍。成本是
O(W×H)，与"新增了多少数据"无关。

**1200×600 是 126% 的帧预算——一个放大的 Spectrogram 单独就跟不上帧率了。** 而画新增的那一列
只要 0.016 ms，差三个数量级。

两条分支（稠密路径与逐行路径）都是 O(W×H)，所以分支选择不是杠杆，**重绘本身才是**。

### 已落地：把每像素 4 次字节写压成 1 次 32 位写

`paintSpan` 原本每个像素写 4 次 `data[idx+n]`，现在对 `Uint32Array` 视图写一次，颜色表预先打包
成整像素（`packedColormap`，按主题缓存一份）。打包是通过字节视图做的而不是位移，所以字长顺序
跟随平台。输出逐字节相同——`useSpectrogramCanvas.test.jsx` 里那两个像素字节断言原样通过。

收益 **−7%**（600×300：6.09 → 5.70 ms）。真实，但不解决问题。

### 量过：把颜色math内联进像素循环还能再省约 20%

benchmark 里的 `full, colour math inlined` 一行衡量的就是每像素那次 `spectrogramColorFrac`
调用的代价（1200×600：20.1 → 15.4 ms）。**没有做**：它要把色阶公式从主题模块复制进画笔，
而 15.4 ms 依然超预算——付出重复定义的代价，换一个仍然不够的数字，不划算。

### 3D 采样核心：不是瓶颈，但这不代表整条 3D 路径都不是

| | 每帧 | 占预算 |
| --- | --- | --- |
| 600×300，64 脊 × 600 点 | 0.85 ms | 5% |
| 600×300，160 脊 × 600 点 | 1.63 ms | 10% |
| 1200×600，64 脊 × 958 点 | 1.05 ms | 7% |
| 1200×600，160 脊 × 958 点 | 2.62 ms | 16% |

`sampleWaterfallGrid` 的成本随脊数线性增长，最坏 16% 预算。**比当时的 2D 整幅重画便宜一个数量级**，
因为它采样的是几十条脊而不是每一个像素。这个 benchmark 只覆盖两种 3D mode 共用的历史采样，
没有覆盖 Lines 的路径提交，也没有覆盖 Surface 的平滑、逐像素 rasterize、`putImageData` 和最终合成。
所以这里只能判定采样核心不用动；此前把它写成“3D 路径不是瓶颈”是把局部数字外推过头了。

### 3D 两种 mode 的真实窗口对拍（2026-08-31）

Windows WebView2、VB-Cable + VLC 实时信号；Spectrogram 全屏，CSS 画布 1107×512、device canvas
1383×640；同一时间范围、视角、色彩与网格参数。先预热并填满历史，再让内置 panel CPU 计数器各跑
10 秒。绘制命令计数另跑 5 秒，避免计数器本身污染计时。

| mode | 实际重画 | callback 总耗时 | 平均每 callback | 最大值 | 主线程成本 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **3D Lines** | 109 / 10 s | 191.4 ms | **1.74 ms** | 5.7 ms | **19.1 ms/s** |
| **3D Surface** | 117 / 10 s | 1305.1 ms | **10.97 ms** | 24.6 ms | **130.5 ms/s** |
| **3D Surface（复测）** | 94 / 10 s | 1088.1 ms | **11.58 ms** | 71.6 ms | **108.8 ms/s** |

Surface 稳态每帧是 Lines 的 **6.3–6.7 倍**，并把实际刷新从 Lines 的约 11–12 次/秒压到约
9–12 次/秒。Surface 的离群帧还到过 71.6 ms；不是每帧都发生，但已经足够造成肉眼可见的卡顿风险。

结构计数解释了差异：Lines 每次重画提交约 101 次 `stroke`；Surface 每次重画只做一次
`putImageData` 和一次 `drawImage`，但在提交前要在 JS 中生成整张 1383×640 像素图。单独的 10 秒
renderer profile 也把 Surface 的 `useSpectrogram3dCanvas` `draw` 列为第一热点（4262 ms，41.3%）；
同样条件切回 Lines 后，它没有进入前 20。profile 会放大采样开销，所以百分比只作热点归因，精确的
mode 对拍以上面的内置 callback 计时为准。

**当时的判定是「Lines 不动，Surface 是下一项 D2 候选」。下一节推翻了前半句**：这张表量的是
主线程，而 `ctx.stroke()` 在光栅化发生之前就返回了。

### 把 GPU 侧也量了之后：成本没有消失，只是换了个进程（2026-08-31）

上一节的两把尺子——面板自己的 rAF 计时器和 renderer profile——都停在「绘制命令提交完毕」。
真正的三角形细分和填色发生在 WebView2 的 GPU 进程里，不在任何一个计时器的账上。补上
`scripts/webview-gpu-usage.mjs`（Windows `GPU Engine` 计数器，按父子链归属到 plvs.exe，见
`README.md`）之后，同一窗口、同一信号、同一 1383×640 device canvas 重测：

| mode | 重画 | 主线程每次 | 主线程 | GPU 3d 引擎 | **GPU 进程 CPU** | CPU 合计 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **3D Lines** | 33.5 / 33.7 次/s | 1.67 / 1.66 ms | 56 ms/s | **14.3% / 17.3%** | **327 / 330 ms/s** | ≈386 ms/s |
| **3D Surface** | 32.8 / 33.8 次/s | 11.68 / 11.36 ms | 383 ms/s | 7.2% / 7.6% | 6.3 / 6.3 ms/s | ≈390 ms/s |
| 2D Heatmap | 34.6 次/s | 1.07 ms | 37 ms/s | 6.6% | 10.9 ms/s | ≈48 ms/s |
| 底线（停止采集） | 0 | — | — | **0.00%** | **0.0 ms/s** | 0 |

（每档 10 秒，A/B/A/B 交替；底线读数是 0，所以上面每一行都可以整份记到面板头上。GPU 进程 CPU
的量级另用一次独立的 `Get-Process` 采样复核过：Lines 245 ms/s、Surface 9.4 ms/s——同一方向，
绝对值略低，因为那次设置浮层还盖着一部分画布。）

三条结论：

1. **两个 mode 的 CPU 总账几乎相等（386 vs 390 ms/s）。** Lines 不是更便宜，它只是把同一份活
   从渲染进程搬到了 GPU 进程：主线程省下的 327 ms/s，在 GPU 进程里几乎一分不少地又花掉了。
   上一节「Surface 是 Lines 的 6.3–6.7 倍」是只看渲染进程得出的，成立但不完整。
2. **GPU 引擎这一侧 Lines 是 Surface 的约 2.2 倍**（14.3–17.3% vs 7.2–7.6%），也是全部四档里
   最高的。用户先感觉到的就是这一项。
3. **两个 mode 的重画频率一致（约 33 次/s）**，所以上面每秒的数字可以直接比。此前那张表里
   Lines 约 11 次/s 是另一组时间轴参数下的读数，不要跨表比较。

结构计数给出了原因，同一次会话里数的：

| mode | 每次重画提交 |
| --- | --- |
| 3D Lines | **98.5 次 `stroke`**（2693 次/秒），每条脊一次 |
| 3D Surface | 1 次 `putImageData` + 1 次 `drawImage` + 2 次 `stroke`（地面网格） |

每条脊是一条约 230 点、`lineJoin: "round"`、线宽 `dpr × 1.5` 的折线，且**每条脊都新建一个
17 stop 的 `createLinearGradient`**（`buildRidgeGradient`）。约 100 次不可批处理的描边、约 2.3 万
段几何、约 100 次画笔状态切换——这就是那 327 ms/s 和 14–17% 的去处。Surface 反过来：整张图在 JS
里逐像素算完，GPU 只做一次约 3.5 MB 的纹理上传。

**修订后的判定：两个 mode 都是 D2 候选，但不是同一个问题。** Surface 的问题在渲染进程的逐像素
rasterize；Lines 的问题在提交给 GPU 的绘制命令结构——先分清是那 100 个渐变还是那 2.3 万段几何在
花钱，再决定改法（按色阶分桶批量描边 / `lineJoin` 改 bevel / 降密度）。在共用的
`sampleWaterfallGrid` 上抠时间对两者都无效。

## 2. 已落地：滚动复用（2026-08-29）

实时窗口只是向前走时，把已画的图整体左移，只重画新进来的那一条。

| | 改前 | 改后 | 占预算 |
| --- | --- | --- | --- |
| 600×300 | 5.50 ms | **0.050 ms** | 34% → **0.3%** |
| 1200×600 | 19.33 ms | **0.203 ms** | **121% → 1.3%** |

大面板从**超出帧预算**变成 1.3%。

### 为什么可以这么做，以及它凭什么不出错

图像的最左列代表的时刻由 `paintedOldestMs` 记着，**不等于**窗口真正的 `oldestMs`——两者允许
相差不到一列。`spectrogramScrollPlan` 每帧算出该滑几个整像素，并把新的原点**返回**而不是从窗口
重新推导，所以那点零头永远被记着、永远不累积。测试里跑一万帧之后仍然断言滞后 < 1 列。

60 秒窗口铺在 600 像素上，一行 40 ms 只占 **0.4 像素**——所以多数帧根本不该移动。这类帧只重画
最右一列（一行数据会先落进那一列，才慢慢挣到属于自己的一列），代价可忽略。

### 安全边界写成了"只有时间在动"

`slidable` 的判定是正向白名单：实时模式、非冻结、同一个 view、span 与 sampleMs 未变、窗口只向前。
**任何一条不满足就整幅重绘。** 写成"只有时间在动"而不是"以下情况需要失效"，是为了让以后新增的
控件默认走不进滚动路径，而不是悄悄留下一张过期的图。

缩放、平移、改 dB Floor / Tilt / 主题色阶、改尺寸或频率范围、拖动回放——全部落回原路径。

### 保证正确性的那个测试

`sliding versus repainting` 连续滑 200 帧，然后拿同一时刻**从零重绘**的图逐字节比对，必须完全
相同。另有一个用例专门验证时间轴上的真实空隙不会被滑过去的旧像素糊住。

写这个测试时它一开始就红了——查出来是我夹具里 `timestampAt` 越界（`spectrogramFrameEndMs` 会
读 index+1），不是实现的问题。这正是这类等价测试的价值：它逼着人分清"实现错了"和"测试错了"。

## 3. 原始待决策记录（已解决，保留推理过程）

真正的修法是**别重绘没变的部分**：把已有图像整体左移，只画新进来的那一列。稳态成本从
5.7 / 20.1 ms 降到 0.008 / 0.016 ms 量级。

但它把重绘语义从"无状态"改成"有状态"，要处理的情况不止一种：

- **窗口每帧前进的像素数不是整数**（1500 行落在 600 像素上，每行 0.4 px），整数化的滚动会累积漂移
- **缩放、平移、改窗口长度**都会让 x↔时间的映射整体改变，必须全量重绘
- **改 dB Floor、tilt、主题色阶**会改变每个像素，必须全量重绘
- **画布尺寸变化**同上
- **快照/拖动回放**模式下窗口是冻结的，不滚动
- **时间轴上的真实空隙**当前是靠"不画"来表达透明，滚动复用时要保证空隙不会被旧像素填上

每一条都有对应的失效模式，且都是视觉上很显眼的那种（拖影、错位、空隙被糊住）。这是一次真正的
设计改动，不是局部优化，所以停在这里等决策。

## 3.5 滚动路径实际有没有被走到（2026-08-29，实测）

滚动复用做完之后，profile 里 `paintSpan` 仍然排第一（4.2%）。这个问号只能靠计数回答，
所以给两条路径各加了一个计数器，并把应用自带的面板 CPU 计数器改成**发布构建里也挂上**——
渲染性能采样跑的就是发布构建，只在开发构建里暴露等于把仪器锁在了它唯一有用的场合之外。
（计数默认关闭，要显式打开。）

### 结果：文件分析模式下一次都没走到，原因是窗口长度每帧都在变

第一次测：8 秒 256 次绘制，**256 次全是整幅重绘**。

于是查条件。发现两处我写错的地方：

1. **`sampleMs` 不该进判定。** 它是"最后两行的间隔"，随调度抖动，逐帧相等是不可能满足的。
   而它只影响**最右一列**和空隙边缘（`spectrogramFrameEndMs` 对其余行取下一行的时间戳），
   最右一列本来就每帧重画。已移出。
2. **`span` 也不该要求精确相等。** 窗口两端是历史时间戳，长度天然有毫秒抖动。改成**按像素判**：
   只要图像的映射与实时映射相差不到半列，图就还是对的图。而且是拿"图当初绘制时的 span"
   做基准而不是上一帧的，这样缓慢漂移也不会累积过半列。

改完再测，仍然 353/353 整幅重绘。加上"被哪个条件挡住"的计数后，答案是
**`spanChanged`，353/353**——文件分析模式下窗口长度每帧的变化**真的**超过半列。

这不是抖动，是真的变了：文件分析按批推进，一帧内窗口滑过很多行，而那些行的时间间隔并不均匀。
对这种情况，整幅重绘是**正确的选择**——滑动会把像素放错位置。

### 所以现状是

- 滚动复用的**正确性**有测试保证（200 帧滚动后与从零重绘逐字节相同）。
- 它在**文件分析模式下不生效**，而且不该生效。
- 当时在**实时采集下是否生效无法验证**——远程会话里拿不到音频设备，唯一能产生帧的途径就是
  文件分析。后来 capture rig 已经打通，实测结果见 §3.6。

最坏情况它是惰性的（退回改动前的行为），最好情况是 100 倍。要确认，在本机会话里开着实时采集
跑一条命令即可：

```js
const p = window.__PLVS_PANEL_CPU__;
p.reset(); p.enable();
setTimeout(() => { p.disable(); console.table(p.snapshot()); }, 8000);
```

看 `spectrogram2d:slidStrip` 与 `spectrogram2d:fullRepaint` 的比例；若仍被挡住，
`spectrogram2d:noSlide:<原因>` 会直接说是哪一条。

## 3.6 实时滚动路径已验证（2026-08-31）

Windows WebView2、VB-Cable + VLC 实时信号，同一真实窗口计 10 秒：

| 事件 | 次数 |
| --- | ---: |
| scheduled / callback | 197 / 197 |
| signature skip | 23 |
| **实际绘制（dirty paint）** | **174** |
| **slid strip** | **160** |
| full repaint | 14 |
| `noSlide:spanChanged` | 14 |

**160 / 174 = 92.0% 的脏帧走滚动条带。** 剩余 14 次全图重画都有明确的 `spanChanged` 原因，
是完整 paint signature 的正确性回退，不是优化失效。此前文件分析 353/353 全图重画与这次 Live
160/174 滚动并不矛盾：前者一批跨过多行、窗口映射每帧真变；后者按实时节奏前进，绝大多数帧只需
滑动已有像素再补右侧新条带。这一项关闭。

## 4. 首次 renderer profile（2026-08-29）

通过**文件分析**取到了——不需要音频设备，远程会话也能跑，方法见 `README.md`。
10 秒、17981 个样本，采的是已经带上滚动复用的生产构建。

**Spectrogram 的画笔没有出现在排行前列。** 唯一能确认与它相关的是 `dbAt`（172 ms，1.7%），
而那是 Spectrum 和 Spectrogram 共用的行解码器。滚动复用之后，2D 画笔不再是热点。

`putImageData` 的上传也没有单独浮出来。它仍然每帧传一整幅 RGBA
（600×300 = 720 KB，1200×600 = 2.88 MB），但在这次采样里没有构成可见的自耗时——
**先不动它**，等有面板证据再说。

### 采到的两条线索都不属于 Spectrogram

| 原生 API | 自耗时 | 归属 |
| --- | --- | --- |
| `getPropertyValue` | 311 ms (3.1%) | 每帧读主题 token |
| `addColorStop` | 211 ms (2.1%) | 每帧重建 canvas 渐变 |

`getComputedStyle` 已确认落在两处**每帧绘制路径**里——`WaveformPanel.jsx:115` 与
`VectorscopePanel.jsx:263`——读的都是只在换主题时才变的值。`StereoMapPlot.jsx:386` 的注释
本身就警告过这会强制同步样式重算。

`addColorStop` 只有两个调用点（`StereoMapPlot.jsx:213`、`useSpectrogram3dCanvas.js:253`），
都不在默认布局里，所以它来自采样当时那台机器恢复出来的布局。**归因待定。**

这两条都不是 Spectrogram 的问题，留给 Waveform、Vectorscope、Stereo Map 各自那一轮，
或者作为一次横切修复（"主题 token 每帧只读一次"）单独做。
