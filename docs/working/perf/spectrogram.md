# Spectrogram 体检表

**状态：** D1、D3、D4 继承自 Spectrum，无独立工作；D2 已测并已落地滚动复用。

## 0. 继承关系（先钉死，免得重做）

Spectrogram 不是一个独立的数据管线，它和 Spectrum 共用同一份东西：

| 维度 | 情况 |
| --- | --- |
| **D1 Rust 计算** | 完全继承。`SpectrogramPanel` 用的就是 `spectrumRequestKeyFromControls`，同一个 key、同一批 consumer、同一个 96 点/八度栅格。见 `spectrum.md` §1.5、§1.8 |
| **D3 历史存储** | 完全继承。它读的是 `getSpectrogramSnapsForKey(key)`，也就是 Spectrum 写进去的**同一块 `SpectrumHistorySlab`**。见 `spectrum.md` §3.0 |
| **D4 传输** | 完全继承。行、栅格、payload 都是 Spectrum 那条链路的。见 `spectrum.md` §3.5、§3.6 |
| **D2 前端渲染** | **唯一的独立面** —— 两条画布路径都是它自己的 |

所以这一轮实质上只有 D2。

## 1. D2 实测（2026-08-29）

工具：`npm run benchmark:spectrogram-render`。两条画笔都是对历史行的纯计算，可脱离应用测；
`putImageData` 的上传与画布合成仍在测量范围之外。

条件：958 频带、60 秒窗口（1500 行）、16 ms 帧预算。

| | 每帧 | 占预算 |
| --- | --- | --- |
| 600×300 整幅重绘 | 5.70 ms | **36%** |
| 600×300 只画新增一列 | 0.008 ms | 0.1% |
| 1200×600 整幅重绘 | 20.14 ms | **126%** |
| 1200×600 只画新增一列 | 0.016 ms | 0.1% |

### 主结论：**每帧重绘整幅图，而每帧只有一列是新的**

`paintSpectrogramImageData` 开头就是 `words.fill(0)`，然后把窗口内所有行重画一遍。成本是
O(W×H)，与"新增了多少数据"无关。

**1200×600 是 126% 的帧预算——一个放大的 Spectrogram 单独就跟不上帧率了。** 而画新增的那一列
只要 0.016 ms，差三个数量级。

两条分支（稠密路径与逐行路径）都是 O(W×H)，所以分支选择不是杠杆，**重绘本身才是**。

### 已落地：把每像素 4 次字节写压成 1 次 32 位写

`paintSpan` 原本每个像素写 4 次 `data[idx+n]`，现在对 `Uint32Array` 视图写一次，颜色表预先打包
成整像素（`packedColormap`，按主题缓存一份）。打包是通过字节视图做的而不是位移，所以字长顺序
跟随平台。输出逐字节相同——`useSpectrogramCanvas.test.jsx` 里那两个像素字节断言原样通过。

收益 **−7%**（600×300：6.09 → 5.70 ms）。真实，但不解决问题。

### 量过：把颜色math内联进像素循环还能再省约 20%

benchmark 里的 `full, colour math inlined` 一行衡量的就是每像素那次 `spectrogramColorFrac`
调用的代价（1200×600：20.1 → 15.4 ms）。**没有做**：它要把色阶公式从主题模块复制进画笔，
而 15.4 ms 依然超预算——付出重复定义的代价，换一个仍然不够的数字，不划算。

### 3D 路径：不是瓶颈

| | 每帧 | 占预算 |
| --- | --- | --- |
| 600×300，64 脊 × 600 点 | 0.85 ms | 5% |
| 600×300，160 脊 × 600 点 | 1.63 ms | 10% |
| 1200×600，64 脊 × 958 点 | 1.05 ms | 7% |
| 1200×600，160 脊 × 958 点 | 2.62 ms | 16% |

`sampleWaterfallGrid` 的成本随脊数线性增长，最坏 16% 预算。**比 2D 便宜一个数量级**，
因为它采样的是几十条脊而不是每一个像素。这一侧不需要动。

## 2. 已落地：滚动复用（2026-08-29）

实时窗口只是向前走时，把已画的图整体左移，只重画新进来的那一条。

| | 改前 | 改后 | 占预算 |
| --- | --- | --- | --- |
| 600×300 | 5.50 ms | **0.050 ms** | 34% → **0.3%** |
| 1200×600 | 19.33 ms | **0.203 ms** | **121% → 1.3%** |

大面板从**超出帧预算**变成 1.3%。

### 为什么可以这么做，以及它凭什么不出错

图像的最左列代表的时刻由 `paintedOldestMs` 记着，**不等于**窗口真正的 `oldestMs`——两者允许
相差不到一列。`spectrogramScrollPlan` 每帧算出该滑几个整像素，并把新的原点**返回**而不是从窗口
重新推导，所以那点零头永远被记着、永远不累积。测试里跑一万帧之后仍然断言滞后 < 1 列。

60 秒窗口铺在 600 像素上，一行 40 ms 只占 **0.4 像素**——所以多数帧根本不该移动。这类帧只重画
最右一列（一行数据会先落进那一列，才慢慢挣到属于自己的一列），代价可忽略。

### 安全边界写成了"只有时间在动"

`slidable` 的判定是正向白名单：实时模式、非冻结、同一个 view、span 与 sampleMs 未变、窗口只向前。
**任何一条不满足就整幅重绘。** 写成"只有时间在动"而不是"以下情况需要失效"，是为了让以后新增的
控件默认走不进滚动路径，而不是悄悄留下一张过期的图。

缩放、平移、改 dB Floor / Tilt / 主题色阶、改尺寸或频率范围、拖动回放——全部落回原路径。

### 保证正确性的那个测试

`sliding versus repainting` 连续滑 200 帧，然后拿同一时刻**从零重绘**的图逐字节比对，必须完全
相同。另有一个用例专门验证时间轴上的真实空隙不会被滑过去的旧像素糊住。

写这个测试时它一开始就红了——查出来是我夹具里 `timestampAt` 越界（`spectrogramFrameEndMs` 会
读 index+1），不是实现的问题。这正是这类等价测试的价值：它逼着人分清"实现错了"和"测试错了"。

## 3. 原始待决策记录（已解决，保留推理过程）

真正的修法是**别重绘没变的部分**：把已有图像整体左移，只画新进来的那一列。稳态成本从
5.7 / 20.1 ms 降到 0.008 / 0.016 ms 量级。

但它把重绘语义从"无状态"改成"有状态"，要处理的情况不止一种：

- **窗口每帧前进的像素数不是整数**（1500 行落在 600 像素上，每行 0.4 px），整数化的滚动会累积漂移
- **缩放、平移、改窗口长度**都会让 x↔时间的映射整体改变，必须全量重绘
- **改 dB Floor、tilt、主题色阶**会改变每个像素，必须全量重绘
- **画布尺寸变化**同上
- **快照/拖动回放**模式下窗口是冻结的，不滚动
- **时间轴上的真实空隙**当前是靠"不画"来表达透明，滚动复用时要保证空隙不会被旧像素填上

每一条都有对应的失效模式，且都是视觉上很显眼的那种（拖影、错位、空隙被糊住）。这是一次真正的
设计改动，不是局部优化，所以停在这里等决策。
