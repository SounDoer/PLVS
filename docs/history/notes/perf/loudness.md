## 1. D1 — Rust 计算

### 1.1 唯一那个测试不测任何东西

`dsp::loudness::tests::measure_reference_files` 看起来像一致性测试，其实不是：

- 素材目录 `dialogue-test-audio/` 不在仓库里，缺失时它 `println!("SKIP")` 然后 `continue`；
- **即使素材在，它也只 `println!` integrated 和 LRA，没有任何 `assert`。**

所以 momentary / short-term / integrated / LRA 的**数值**此前没有任何断言守着。
（true peak 的同类缺口在 Level Meter 轮已补，见 `level-meter.md`。）

### 1.2 已补：三条能对着标准验算的断言

`integrated_loudness_matches_bs1770_for_a_known_tone` 用 1 kHz 稳态正弦：

| 断言 | 实测 | 依据 |
| --- | ---: | --- |
| −20 dBFS 立体声 | **−19.9933 LUFS** | LKFS = −0.691 + 10·log10(Σz)，反推 K 加权在 1 kHz 为 **+0.698 dB** |
| 振幅翻倍 | **+6.0206 LU** | 恰好 20·log10 2 |
| 增加一个相同声道 | **+3.0103 LU** | 恰好 10·log10 2，声道按**功率**相加 |

第一条是绝对锚点，同时压住 K 加权、声道求和与 −0.691 偏移——而它读出 −20.0 正是因为那个
偏移和 1 kHz 处的搁架增益几乎抵消。后两条是纯比例关系，不依赖任何滤波器细节，
所以即使实现换了滤波器实现也应当成立。

## 2. D2 — 前端渲染

### 2.1 时间轴的 tick 每次改标签都在重挂节点（三个面板共有）

DOM 计数器显示 Loudness、Waveform、Spectrogram **各有 76.8 次/秒的节点增删**——三个数字完全
相同，说明来自共用组件。

查出来是 `AxisRail` 的 tick key 写成了 `` `${i}-${tick}` ``，**把标签文本编进了 key**。
时间标签几乎每次更新都在变（"5.0s ago" → "4.9s ago"），于是 React 每次都当成新元素：
卸载旧 `<span>`、构造并挂载新的，而不是改一个文本节点。

三处（`LoudnessHistoryChart`、`SpectrogramPanel`、`WaveformPanel`）改成按槽位 key。实测：

| 面板 | 改前 | 改后 |
| --- | --- | --- |
| Loudness | 180.1/s（节点 77.2） | **142.8/s（节点 0，文本 38.8）** |
| Waveform | 76.8/s（全是节点） | **38.8/s（全是文本）** |
| Spectrogram | 76.8/s（全是节点） | **38.8/s（全是文本）** |

正好减半：每次改标签的"删一个 + 加一个"变成了"写一次文本"，而且剩下那一次是廉价的
`textContent` 写入，不再构造元素、赋类名、插入。

`AxisRail.test.jsx` 加了一条断言：改标签后 DOM 节点必须是**同一个对象**。

### 2.2 历史查询才是这个面板的成本，不是绘制

profile 里 Loudness 的绘制没进前列，但**历史查询路径合计约 6%**：
`queryRangeValues` 2.5% + `PowerOfTwoMinMaxIndex` 1.5%+0.6% + `historyMath` 1.4%。

原因是结构性的：长窗口里的行数远多于图表列数，所以构建一次路径要**按列各查一次极值**——
600 像素就是 600 次查询，每次更新都做。

#### 先猜错了一次

第一反应是"每访问一个原始行就新建一个数组加一个对象"，改成 scratch 复用后**没有任何变化**
（1.244 → 1.221 ms，噪声内）。让基准报出遍历构成才看清：

```
One 600 px build over 4 h: 600 queries, 3,712 summary buckets, 0 raw rows (0.0% raw)
```

**原始行一个都没访问。** 长窗口全部由汇总桶回答，我优化的那条路径根本不执行。改动已撤销。

#### 真正的成本：每个桶都从最高层往下扫

`queryRange` 对每个位置从 `_maxLevel` 逐层往下试，而层级其实被**两件事**同时框死：
`sequence` 的对齐程度（末尾有几个零）和剩余行数。36 万行时 `_maxLevel` 约 18，
于是每找一个桶要白试十几层，而一次构建要找三千多个桶。

改成直接算出起始层（`Math.clz32` 求末尾零与 log2）。**这只是提示，不是判断**：循环内部
仍然自己检查宽度与对齐，所以算错只会更慢——提示偏低会多合并几个桶得到同一答案
（min/max 可结合），偏高则在入口被拒。另外把每次命中都新建的桶包装对象改成复用。

| | 改前 | 改后 |
| --- | ---: | ---: |
| 4h 窗口 / 600 px | 1.244 ms | **0.793 ms**（−36%） |
| 4h 窗口 / 1200 px | 2.632 ms | **1.816 ms**（−31%） |
| 10 分钟窗口 / 600 px | 1.002 ms | **0.547 ms**（−45%） |

桶数完全没变（3,712），证实分解方式未变、只是少试了不可能的层。

**Waveform 用同一个索引，一并受益**（实测对照）：

| | 改前 | 改后 |
| --- | ---: | ---: |
| 600px / 7200s | 0.645 ms | **0.363 ms**（−44%） |
| 1200px / 7200s | 1.117 ms | **0.614 ms**（−45%） |

新增等价测试：对 600 行、多种起点与跨度穷举，结果必须与朴素扫描逐一相同。
（夹具用 `Math.fround`——索引存 Float32，见 `AGENTS.md`。）

## 3. D3 — 历史存储

Loudness 历史是标量：每行 `m` 与 `st` 两个值，加 `PowerOfTwoMinMaxIndex` 的分层极值摘要。
`npm run benchmark:history` 已覆盖。相对 Stereo Map 的 958 频带行，这里的体量小两个数量级，
**没有可挤的水分**。

## 4. D4 — payload

loudness 标量（momentary / shortTerm / integrated / lra / mMax / stMax）随每帧发送，
每个一个 f64，无数组、无 per-band 结构。文件分析另有 `loudness_hist_batch` 按 checkpoint 节奏。
**无独立开销可省。**
