# Spectrogram 体检表

**状态：** D1、D3、D4 继承自 Spectrum，无独立工作；D2 的 2D 路径已落地滚动复用；3D Lines 的 GPU
成本已定位到描边宽度并已修复（GPU 14–17% → 4.6%）；3D Surface 已迁到 WebGL（主线程每次重画
7.10 → 3.09 ms）；两个 3D mode 共有的 10 Hz 推进停顿已改为只在绘制层跟随 25 Hz visual 时间戳。
Surface 轮廓沸腾未消除，已与用户确认接受现状。

## 0. 继承关系（先钉死，免得重做）

Spectrogram 不是一个独立的数据管线，它和 Spectrum 共用同一份东西：

| 维度 | 情况 |
| --- | --- |
| **D1 Rust 计算** | 完全继承。`SpectrogramPanel` 用的就是 `spectrumRequestKeyFromControls`，同一个 key、同一批 consumer、同一个 96 点/八度栅格。见 `spectrum.md` §1.5、§1.8 |
| **D3 历史存储** | 完全继承。它读的是 `getSpectrogramSnapsForKey(key)`，也就是 Spectrum 写进去的**同一块 `SpectrumHistorySlab`**。见 `spectrum.md` §3.0 |
| **D4 传输** | 完全继承。行、栅格、payload 都是 Spectrum 那条链路的。见 `spectrum.md` §3.5、§3.6 |
| **D2 前端渲染** | **唯一的独立面** —— 两条画布路径都是它自己的 |

所以这一轮实质上只有 D2。

## 1. D2 实测（2026-08-29）

工具：`npm run benchmark:spectrogram-render`。两条画笔都是对历史行的纯计算，可脱离应用测；
`putImageData` 的上传与画布合成仍在测量范围之外。

条件：958 频带、60 秒窗口（1500 行）、16 ms 帧预算。

| | 每帧 | 占预算 |
| --- | --- | --- |
| 600×300 整幅重绘 | 5.70 ms | **36%** |
| 600×300 只画新增一列 | 0.008 ms | 0.1% |
| 1200×600 整幅重绘 | 20.14 ms | **126%** |
| 1200×600 只画新增一列 | 0.016 ms | 0.1% |

### 主结论：**每帧重绘整幅图，而每帧只有一列是新的**

`paintSpectrogramImageData` 开头就是 `words.fill(0)`，然后把窗口内所有行重画一遍。成本是
O(W×H)，与"新增了多少数据"无关。

**1200×600 是 126% 的帧预算——一个放大的 Spectrogram 单独就跟不上帧率了。** 而画新增的那一列
只要 0.016 ms，差三个数量级。

两条分支（稠密路径与逐行路径）都是 O(W×H)，所以分支选择不是杠杆，**重绘本身才是**。

### 已落地：把每像素 4 次字节写压成 1 次 32 位写

`paintSpan` 原本每个像素写 4 次 `data[idx+n]`，现在对 `Uint32Array` 视图写一次，颜色表预先打包
成整像素（`packedColormap`，按主题缓存一份）。打包是通过字节视图做的而不是位移，所以字长顺序
跟随平台。输出逐字节相同——`useSpectrogramCanvas.test.jsx` 里那两个像素字节断言原样通过。

收益 **−7%**（600×300：6.09 → 5.70 ms）。真实，但不解决问题。

### 量过：把颜色math内联进像素循环还能再省约 20%

benchmark 里的 `full, colour math inlined` 一行衡量的就是每像素那次 `spectrogramColorFrac`
调用的代价（1200×600：20.1 → 15.4 ms）。**没有做**：它要把色阶公式从主题模块复制进画笔，
而 15.4 ms 依然超预算——付出重复定义的代价，换一个仍然不够的数字，不划算。

### 3D 采样核心：不是瓶颈，但这不代表整条 3D 路径都不是

| | 每帧 | 占预算 |
| --- | --- | --- |
| 600×300，64 脊 × 600 点 | 0.85 ms | 5% |
| 600×300，160 脊 × 600 点 | 1.63 ms | 10% |
| 1200×600，64 脊 × 958 点 | 1.05 ms | 7% |
| 1200×600，160 脊 × 958 点 | 2.62 ms | 16% |

`sampleWaterfallGrid` 的成本随脊数线性增长，最坏 16% 预算。**比当时的 2D 整幅重画便宜一个数量级**，
因为它采样的是几十条脊而不是每一个像素。这个 benchmark 只覆盖两种 3D mode 共用的历史采样，
没有覆盖 Lines 的路径提交，也没有覆盖 Surface 的平滑、逐像素 rasterize、`putImageData` 和最终合成。
所以这里只能判定采样核心不用动；此前把它写成“3D 路径不是瓶颈”是把局部数字外推过头了。

### 3D 两种 mode 的真实窗口对拍（2026-08-31）

Windows WebView2、VB-Cable + VLC 实时信号；Spectrogram 全屏，CSS 画布 1107×512、device canvas
1383×640；同一时间范围、视角、色彩与网格参数。先预热并填满历史，再让内置 panel CPU 计数器各跑
10 秒。绘制命令计数另跑 5 秒，避免计数器本身污染计时。

| mode | 实际重画 | callback 总耗时 | 平均每 callback | 最大值 | 主线程成本 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **3D Lines** | 109 / 10 s | 191.4 ms | **1.74 ms** | 5.7 ms | **19.1 ms/s** |
| **3D Surface** | 117 / 10 s | 1305.1 ms | **10.97 ms** | 24.6 ms | **130.5 ms/s** |
| **3D Surface（复测）** | 94 / 10 s | 1088.1 ms | **11.58 ms** | 71.6 ms | **108.8 ms/s** |

Surface 稳态每帧是 Lines 的 **6.3–6.7 倍**，并把实际刷新从 Lines 的约 11–12 次/秒压到约
9–12 次/秒。Surface 的离群帧还到过 71.6 ms；不是每帧都发生，但已经足够造成肉眼可见的卡顿风险。

结构计数解释了差异：Lines 每次重画提交约 101 次 `stroke`；Surface 每次重画只做一次
`putImageData` 和一次 `drawImage`，但在提交前要在 JS 中生成整张 1383×640 像素图。单独的 10 秒
renderer profile 也把 Surface 的 `useSpectrogram3dCanvas` `draw` 列为第一热点（4262 ms，41.3%）；
同样条件切回 Lines 后，它没有进入前 20。profile 会放大采样开销，所以百分比只作热点归因，精确的
mode 对拍以上面的内置 callback 计时为准。

**当时的判定是「Lines 不动，Surface 是下一项 D2 候选」。下一节推翻了前半句**：这张表量的是
主线程，而 `ctx.stroke()` 在光栅化发生之前就返回了。

### 把 GPU 侧也量了之后：成本没有消失，只是换了个进程（2026-08-31）

上一节的两把尺子——面板自己的 rAF 计时器和 renderer profile——都停在「绘制命令提交完毕」。
真正的三角形细分和填色发生在 WebView2 的 GPU 进程里，不在任何一个计时器的账上。补上
`scripts/webview-gpu-usage.mjs`（Windows `GPU Engine` 计数器，按父子链归属到 plvs.exe，见
`README.md`）之后，同一窗口、同一信号、同一 1383×640 device canvas 重测：

| mode | 重画 | 主线程每次 | 主线程 | GPU 3d 引擎 | **GPU 进程 CPU** | CPU 合计 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **3D Lines** | 33.5 / 33.7 次/s | 1.67 / 1.66 ms | 56 ms/s | **14.3% / 17.3%** | **327 / 330 ms/s** | ≈386 ms/s |
| **3D Surface** | 32.8 / 33.8 次/s | 11.68 / 11.36 ms | 383 ms/s | 7.2% / 7.6% | 6.3 / 6.3 ms/s | ≈390 ms/s |
| 2D Heatmap | 34.6 次/s | 1.07 ms | 37 ms/s | 6.6% | 10.9 ms/s | ≈48 ms/s |
| 底线（停止采集） | 0 | — | — | **0.00%** | **0.0 ms/s** | 0 |

（每档 10 秒，A/B/A/B 交替；底线读数是 0，所以上面每一行都可以整份记到面板头上。GPU 进程 CPU
的量级另用一次独立的 `Get-Process` 采样复核过：Lines 245 ms/s、Surface 9.4 ms/s——同一方向，
绝对值略低，因为那次设置浮层还盖着一部分画布。）

三条结论：

1. **两个 mode 的 CPU 总账几乎相等（386 vs 390 ms/s）。** Lines 不是更便宜，它只是把同一份活
   从渲染进程搬到了 GPU 进程：主线程省下的 327 ms/s，在 GPU 进程里几乎一分不少地又花掉了。
   上一节「Surface 是 Lines 的 6.3–6.7 倍」是只看渲染进程得出的，成立但不完整。
2. **GPU 引擎这一侧 Lines 是 Surface 的约 2.2 倍**（14.3–17.3% vs 7.2–7.6%），也是全部四档里
   最高的。用户先感觉到的就是这一项。
3. **两个 mode 的重画频率一致（约 33 次/s）**，所以上面每秒的数字可以直接比。此前那张表里
   Lines 约 11 次/s 是另一组时间轴参数下的读数，不要跨表比较。

结构计数给出了原因，同一次会话里数的：

| mode | 每次重画提交 |
| --- | --- |
| 3D Lines | **98.5 次 `stroke`**（2693 次/秒），每条脊一次 |
| 3D Surface | 1 次 `putImageData` + 1 次 `drawImage` + 2 次 `stroke`（地面网格） |

每条脊是一条约 230 点、`lineJoin: "round"`、线宽 `dpr × 1.5` 的折线，且**每条脊都新建一个
17 stop 的 `createLinearGradient`**（`buildRidgeGradient`）。约 100 次不可批处理的描边、约 2.3 万
段几何、约 100 次画笔状态切换——这就是那 327 ms/s 和 14–17% 的去处。Surface 反过来：整张图在 JS
里逐像素算完，GPU 只做一次约 3.5 MB 的纹理上传。

### Lines 的归因：不是渐变，不是 join，是「线宽超过 1 device px」（2026-08-31）

三个假设各做一臂，用 CDP 在运行时改画笔属性（几何完全不动，只换画法），A/B 中间夹对照：

| 臂 | GPU 3d | GPU 进程 CPU | 重画 |
| --- | ---: | ---: | ---: |
| 对照（原样） | 16.89% | 287.5 ms/s | 37.7/s |
| 每脊渐变 → 纯色 | 17.28% | 254.7 ms/s | 37.5/s |
| `lineJoin` round → bevel | 16.54% | 221.9 ms/s | 37.1/s |
| **线宽 → 1 device px** | **3.83%** | **14.1 ms/s** | 38.0/s |
| 纯色 + bevel | 16.00% | 240.6 ms/s | 38.0/s |
| 对照（复测） | 16.79% | 243.8 ms/s | 37.7/s |

**前两个假设都是错的。** 那约 100 个 `createLinearGradient` 和 round join 加起来动不了大局；
把线宽压到 1 device px 却让 GPU 掉到 1/4、GPU 进程 CPU 掉到 1/20。

线宽扫描说明这是个悬崖，不是斜坡：

| 线宽（device px） | 1 | 0.99 | 1.05 | 1.25 | 1.5 | 1.875（现状） | 3 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| GPU 3d | 3.25% | 3.42% | 16.15% | 16.08% | 16.80% | 14.5–14.8% | 13.3–14.9% |
| GPU 进程 CPU | 1.6 | 0.0 | 245.3 | 257.8 | 209.4 | 217–259 | 237–272 |

阈值精确落在 **1 device px**，越过之后到 3 px 都是平的。这是 Skia 的 hairline 快路径边界：
宽度 ≤1 的描边直接走线段光栅化，>1 就要把每一段折线细分成填充多边形并处理接头。现状的
`dpr × strokeCss` = 1.25 × 1.5 = **1.875**，刚好落在贵的那一侧，而它贵不是因为宽，是因为**过了线**。

所以 Lines 的账其实是：约 100 条脊 × 约 230 点 ≈ 2.3 万段几何，每段都要细分——渐变只是搭车的。

**候选解法已探过一个**：把一次宽描边换成 N 遍 hairline（宽度 1，纵向错开覆盖同样的带宽）。

| 画法 | GPU 3d | GPU 进程 CPU | 主线程每次 |
| --- | ---: | ---: | ---: |
| 对照（一次 1.875 px） | 14.01% / 15.98% | 200.0 / 295.3 ms/s | 1.87 / 1.79 ms |
| 1 遍 hairline | 2.15% | 3.1 ms/s | 1.91 ms |
| **2 遍 hairline** | **3.47%** | **7.8 ms/s** | 1.90 ms |
| 3 遍 hairline | 4.27% | 6.3 ms/s | 1.91 ms |

2 遍覆盖大致同样的视觉厚度，GPU 约为现状的 1/4、GPU 进程 CPU 约为 1/30，主线程不变。

**已落地的是 1 遍**（2026-08-31）：截图对比之后选了最便宜也最简单的一档——脊线固定 1 device
px，不再跟 `--ui-spectrum-stroke-width`，多遍叠加的方案没有采用，也没有留开关。真实 release
构建复测：

| | 改之前 | 改之后 |
| --- | ---: | ---: |
| GPU 3d 引擎 | 14–17% | **4.58%** |
| GPU 进程 CPU | 288–330 ms/s | **5.5 ms/s** |
| 主线程 | 1.7 ms/次 | 1.73 ms/次 |

（改后这一列复核过两次。第一次读到 3.0% / 17.2 ms/s，是在采集源静默回到默认设备、场景几乎空白时
测的——数字偏乐观，作废。上表是地形覆盖 37% 的读数。这个坑见 `README.md` 的采样前置检查一节。）

代价是脊在缩放显示器上比一个 CSS 像素细，这正是当年被反馈为「3D 线看起来变细了」的那个观感，
这次是看过截图后有意接受的取舍。选中脊（scrub 标记）不在此列，它仍读 token——它只有一条，成本
可忽略，而 Surface 的 scrub band 宽度是刻意和它对齐的。

### Surface 的归因与落地：把像素画少一点（2026-08-31）

一次 Surface 重画拆成各阶段（Node 离线，1383×640，属下限）：

| 阶段 | 耗时 | 占比 |
| --- | ---: | ---: |
| **`rasterizeSurface`** | **7.45 ms** | **92.2%** |
| 频率轴平滑 | 0.23 ms | 2.9% |
| 清空缓冲 | 0.17 ms | 2.1% |
| 时间轴平滑 | 0.14 ms | 1.8% |
| rowLut + 恢复高度 | 0.08 ms | 0.9% |

没有意外：两个平滑器、行 LUT、清空加起来不到 8%，唯一能动的杠杆是**走多少像素**。两个旋钮各自
离线扫过（rasterize + clear 的中位数）：

| | 基线 | 列步进 2 | 列步进 3 | 缩放 0.85 | 缩放 0.75 | 缩放 0.6 | 缩放 0.5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 耗时 | 7.89 ms | 4.27 | 2.93 | 5.13 | 4.07 | 2.96 | 1.84 |

**选了缩放，不是列步进**：列步进把每列复制到邻列，是硬边竖条纹；缩放交给 GPU 双线性放大，退化成
柔化，而 GPU 这一侧本来就有余量（此模式只用 5% 的 3d 引擎）。`SURFACE_RENDER_SCALE = 0.75` 落地，
合成从 `drawImage(off.canvas, 0, 0)` 改为拉伸贴回。

真实窗口的受控 A/B（同一信号、同一视角、地形覆盖 37%、每档 60 秒，两臂各自单独构建）：

| | 重画 | 每次重画 | 主线程 | 最大 | GPU 3d | GPU 进程 CPU |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 全分辨率 | 24.4 / 24.6 /s | 12.93 / 12.24 ms | 315 / 301 ms/s | 20.2 / 19.1 ms | 5.02% | 8.6 ms/s |
| **0.75** | 23.3–25.1 /s | **6.59 / 7.40 / 7.24 ms** | **157 / 172 / 181 ms/s** | 19.3 / 21.5 / 19.5 ms | 5.66% | 7.0 ms/s |

**每次重画 −45%，每秒 −45%**，与离线预测的 −48% 一致；GPU 只涨 0.6 个百分点，就是放大那一步的
代价。尾部两臂相同（19–21 ms），**没有恶化**。

代价是山体颗粒变粗、脊线边缘变软，且时间轴可分辨的行数随缓冲高度下降（400 → 约 300）。看过截图
后接受。

### 推进时的抖动（2026-08-31，两种机制）

**这是既有问题，不是缩放引入的。** 受控对拍（每帧记录画面亮度重心，8 秒约 480 帧）：

| | 画面在动的帧 | 一次动多少 | 最大跳变 |
| --- | ---: | ---: | ---: |
| Surface 全分辨率 | 16–17% | 0.21–0.95 px | 0.76–2.67 px |
| Surface 0.75 | 15% | 0.57–0.95 px | 1.45–2.80 px |
| 3D Lines | 14% | 3.5–4.2 px | 13–15 px |

**机制（第二版，第一版是错的）：可见时间窗的边缘只有 10 Hz。**

`SpectrogramPanel` 的 `oldestMs` / `newestMs` 来自 master 时间轴——loudness history，
`HIST_SAMPLE_SEC = 0.1`。`newestMs` 是那条 10 Hz 列表里的一个真实时间戳，所以**窗口边缘每 100 ms
才前进一次**。时间轴投影出约 670 px、窗口约 70 s，画面本应每秒平移约 9.5 px；被 10 Hz 一量化，就
变成"静止 100 ms，然后跳 0.95 px"。实测正好如此：每秒约 10 次位移、每次约 0.95 px，而同期面板每秒
重画 23–25 次——**三分之二的重画画的是同一个窗口位置**。

第一版把原因写成"每次重画移动 0.42 px + 光栅化器整像素取整"，那是把窗口当成连续前进推出来的，
错了。取整确实存在，但它不是主因：主因是那个 0.42 px 的位移根本没有发生过。

**据此写的修复也失败了，一并记下。** 思路是把漂移的小数部分从光栅化里拿掉、在 `drawImage` 合成时
用小数目标坐标还回去（GPU 派的标准手法）。实现后实测无改善：画面在动的帧仍是 16–18%，步长
0.15–1.35 px，而且出现了 1–2 次反向抖动。原因很直接——那个小数部分是用 `p.newestMs` 算的，而
`p.newestMs` 本身就是 10 Hz 的量，一秒只变 10 次，于是补偿量和被补偿的对象同频，什么也没抵消。
代码已回退。

Lines 的步长（3.5–4.2 px，最大 15 px）比这个大一个数量级，后来确认是**第二种机制：绝对时间分箱
重绑**，Lines 和 Surface 共用，因此两边都会发生。`sampleWaterfallGrid` 要求 `sampleMs` 是标称周期，
但 `resolveStableSpectrogramSampleMs` 原先返回最近 16 个实测间隔的最小值。实时帧由 Rust 的 `>= 40ms`
门控在音频回调上发出，整数毫秒时间戳实际得到 40–48ms；当稀疏的短间隔进入或离开回看窗，最小值会
跳 1ms，量化后的 `strideMs` 就跳一整个帧周期。分箱锚在时间原点，约 100 条脊中会有 90 多条同时改绑，
远端一次错开约 15–19px。

离线 harness 直接调用真实的 `resolveStableSpectrogramSampleMs` 和 `sampleWaterfallGrid`：无回调抖动时
120 秒内重绑为 0；0.6ms 抖动时 78 次，中位/最大位移 15.34/19.17px；1.5ms 时 129 次，
14.98/19.76px。量级与 Lines 实测最大 13–15px 对上。原守卫每 9 个间隔必定出现一次 40ms，短于
16 格回看窗，所以最小值从不变化，实际是平凡通过。

**已修：** 稳定周期解析器现在把滑窗最小值匹配到真实生产者的标称周期；live 的 39–48ms 回到
40ms，file 的 99–100ms 回到 100ms。这里不能按任意 10ms 栅格 `round` 或 `floor`：前者会把
45–49ms 推到 50ms，后者会把 39/99ms 降到 30/90ms。守卫让 40ms 短间隔每 60 帧才出现一次，
覆盖其进出回看窗的翻转；另有下边界和 11025Hz 文件累计时间戳的回归。同一批仍在窗口内的脊不得被
重新选择。离线 harness 的 0.6/1.5/3ms 三档重绑均归零。

（0.75 让一个缓冲像素等于 1.33 个屏幕像素，同样的跳变会被放大三分之一。上表的重心指标是整条扫描
线的平均，不足以分辨这个差别，所以这一条是推理而非实测。）

**已落地（2026-09-01）：只让绘制窗口跟随 25 Hz visual 时间戳。** 没有改共享的 master 时间轴；坐标轴、
悬停、marker 与另外两个 timeline panel 仍读原来的 10 Hz 窗口。只有 Live 正在运行、没有 scrub、且
history offset 为 0 时，Spectrogram 的两条画布路径才把窗口整体向最新 visual row 平移，最多补一个
100 ms history interval。文件分析、停止状态、历史回看与选中快照都明确保持原窗口。

这个实现比墙钟外推更窄也更确定：visual timestamp 与 master timestamp 来自同一分析会话，不受系统
时钟跳变、休眠或调度延迟影响；视觉行每 40 ms 已经触发同一批画布回调，所以没有新增 rAF 或重画，只是
让既有回调不再有三分之二拿到相同位置。纯函数钉住 `0 / 40 / 80 ms` 的推进、100 ms 上限与旧时间戳
回退；组件测试钉住 Live 和四条禁入路径。

Heavy 真实窗口 60 秒短测：UI 丢帧 / 音频丢块 `0 / 0`，积压峰值 `8 / 120`，稳态 Long Task `0`，
rAF gap `0`。只出现 3 个与既有基线同形的启动 LoAF；没有新增稳态压力。

### 表面「沸腾」是另一个问题，和整体推进无关（2026-08-31）

用户描述的抖动**不是**上面那个整幅图走走停停，而是**山体表面的锯齿在推进中沸腾，山峰处最明显**。
两者机制不同，指标也不同，先前把它们混为一谈是一次真实的误判。

按每次窗口更新（不是按帧，见 `README.md` 的分母那一节）测到的量级：

| | 轮廓形变 | 跳 ≥1px 的列 | crest 带闪烁 |
| --- | ---: | ---: | ---: |
| 真实窗口 | 0.64–0.68 px | **47–48%** | 6.85–6.95 |
| 离线合成地形 | 0.535 px | 47.8% | 10.5 |

**每次更新有将近一半的轮廓列跳 ≥1 个像素**，这就是沸腾。

**证伪的假设：坡度着色放大噪声。** 着色按相邻两个采样的高度差算，山脊坡度最大，看起来完全对得上；
离线把梯度基线拉长到 8–16 个采样，闪烁从 10.5 掉到 3.3，成本只涨 2%。但真实窗口 A/B（各自单独构建）
**没有改善，甚至略差**（7.69 / 7.32 对 6.85 / 6.95）。原因是离线注入的是每格独立的静态噪声，而真实
数据过了两个平滑器之后，闪烁来自**地形本身在两次更新之间就变了**（新行进来、行间插值权重移动、每列
采样位置漂移），对一个本来就在变的东西做梯度平均没有意义。代码已回退。

（同一轮里还写错过一个测试：断言"长基线让色调变少"。恰恰相反——短基线会把坡度顶到 sigmoid 的饱和端，
饱和端色调更少而闪烁更凶。测试已删，不留一个断言不成立的守卫。）

**当前判定：根因是移动中的噪声地形被重采样。** 离线扫过的杠杆里只有三个能撬动它：

| 杠杆 | 跳 ≥1px 的列 |
| --- | ---: |
| 现状 | 47.8% |
| 平滑器跑两遍 | 40.2% |
| **超采样 1.5×** | **14.0%** |
| 地形完全无噪声 | 23.0% |
| 平滑器关掉 | 72.9% |

最有效的是超采样，而它和已落地的 0.75 渲染缩放方向相反——0.75 买到的 45% CPU 可能有一部分要还回去
换画面稳定。

**三档真实窗口扫描（0.75 / 1.0 / 1.5）跑了，成本这一半可信，抖动那一半作废：**

| 渲染缩放 | 每次重画 | 主线程 | 实际列步进 |
| --- | ---: | ---: | ---: |
| 0.75 | 7.57 ms | 149.5 ms/s | 1 |
| 1.0 | 12.08 ms | 237.6 ms/s | 1 |
| 1.5 | 12.94 ms | 250.0 ms/s | **2** |

**1.5 那一档根本没在做超采样。** `columnStrideFor(2074, 960)` 按面积预算选了 stride 2，也就是隔列采样
再复制——纵向 1.5 倍、横向 0.75 倍。这既解释了它的成本为什么和 1.0 几乎一样（12.94 vs 12.08，而面积是
2.25 倍），也解释了它为什么没有改善抖动。离线那一臂是显式传 `columnStride: 1` 的，所以两边对不上。
**要测超采样必须同时把 stride 钉死为 1**，否则量到的是另一件事。

第二个混淆：同样 8 秒，各臂两轮的"更新次数"从 37 到 86 不等，而**每次更新覆盖的时间越长，跳变的列
自然越多**（0.75 的两轮：86 次更新 → 31.3%，37 次更新 → 54.5%）。这个组内方差盖过了组间差异，所以
三档的抖动数字互相分不开。指标必须按单位时间归一，或者把更新率作为条件固定下来，才能再做比较。

**当前状态：根因是移动中的噪声地形被重采样，这一条有证据；哪个杠杆值得用，没有结论。** 用参数能撬动
的两条路都不划算：超采样要把 stride 钉死为 1，离线估计约 17.7 ms/次重画（现在的 2.3 倍）；平滑器加强
只从 47.8% 到 40.2%，还要赔上地形细节。

### 没有 GPU 时的下限，以及 GPU 路线的可行性（2026-08-31）

GPU 化的最大风险一直是"没有 GPU 的机器怎么办"——驱动黑名单、远程会话、老机器。这是个可以直接量的
问题，用 `--disable-gpu` 起应用即可（WebView2 吃 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`）。

**现有的 CPU 路径几乎不受影响**，符合预期，因为重活在 JS 里：

| | GPU 开 | GPU 关 |
| --- | ---: | ---: |
| Surface | 7.57 ms / 149.5 ms/s | 7.33 ms / 163.2 ms/s |
| Lines | 1.73 ms / 40.3 ms/s | 1.81 ms / 44.6 ms/s |

**关键的一条：`--disable-gpu` 下 WebGL2 仍然可用**，走 ANGLE 的 Microsoft Basic Render Driver
（WARP，软件 D3D11），不是不可用。把一个和真实网格同规模的负载（300 行 × 230 点 = 136,942 个三角形，
画进 1383×640）实测：

| | renderer | 每帧 |
| --- | --- | ---: |
| GPU 开 | ANGLE / RTX 4060 | **1.2 ms**（中位，含回读同步） |
| GPU 关 | ANGLE / Microsoft Basic Render Driver | **13.7 ms** |

所以 GPU 路线在无显卡机器上是 13.7 ms/帧对现在的 7.5 ms——**退化约 1.8 倍，不是不可用**，不需要另外
维护一条 CPU 回退路径。这比做决定之前假设的风险小得多。

> **这一段的结论已被推翻，见本节下方《`--disable-gpu` 下 WebGL Surface 画不出来》。** 这里测的是一个
> 平凡片元着色器的合成负载；真实的 Surface 渲染器在同样的 `--disable-gpu` 下绘制缓冲根本不更新。
> 上面那句"不需要另外维护一条 CPU 回退路径"**不要再引用**。

两条读数时的限定：13.7 ms 含一次同步回读的开销，真实渲染器不会回读，所以偏悲观；而这个片元着色器是
平凡的，真实的要做色标查表、着色和边缘淡出，WARP 是片元瓶颈，这一侧偏乐观。

**别用 `gl.finish()` 或 fence 计时。** 两者在这个栈里都不阻塞：软件驱动下 137k 三角形都报 0.4 ms 中位、
0 ms 最小值，量到的是提交而不是执行。像素回读（`readPixels` 一个像素）是唯一骗不了的屏障。

**当前判定（已由后续结果更新）：Lines 的大幅重绑、Surface 成本与共用的 10 Hz 窗口推进均已解决；
Surface 轮廓沸腾没有消失，但 WebGL A/B 后已与用户确认接受现状。** 成本这条线上，在共用的
`sampleWaterfallGrid` 上继续抠时间对两个 mode 都无效。

### WebGL Surface 落地后的 A/B 对拍（2026-08-31）

两臂都是 release 构建：A 臂 `cb172a74`（落地前的 CPU 光栅化器，渲染缩放 0.75），B 臂 `54b5b1e6`
（WebGL，缩放 1.0）。同一段素材、同一台机器、同一次会话，**覆盖率对齐在 35.6–36.4%**，
Grid 关闭（理由见下）。

| | A 臂 CPU | B 臂 WebGL |
| --- | ---: | ---: |
| 轮廓跳 ≥1px 的列（原口径 alpha>8） | 48.88% | 56.50% |
| 轮廓跳 ≥1px 的列（累积 alpha 口径） | **39.10%** | **35.23%** |
| 轮廓形变（累积 alpha 口径） | 0.884 px | 0.778 px |
| 主线程每次重画 | **7.10 ms**（峰值 20.9） | **3.09 ms**（峰值 5.7） |
| GPU 3d 引擎 | 12.85% | 17.17% |

**沸腾没有解决。** 目标是 47% → <15%（三倍），实测在公平口径下是 39.10% → 35.23%，
相对改善不到 7%。已与用户确认：**接受现状，不回退**——买到的是主线程减半、渲染缩放回到 1.0、
山脊不再是发丝线，以及 MSAA 让每一次位移变成连续的而不是硬跳一格。**位移本身几乎没有变小，
变的是它的呈现方式**，这解释了为什么肉眼判定和指标判定会分歧。

这个结果和机制预测是一致的：本文件上一节已经归因出三个来源（新行进来、行间插值权重移动、
每列采样位置漂移），WebGL 只消掉第三个，前两个是数据管线的性质。

**原口径在抗锯齿面前失效，这是这次最容易上当的地方。** "alpha>8 的最高像素"隐含假设边缘是硬的。
CPU 光栅化器只能把轮廓放在整数像素上，所以它一动就必然跳整格——那个 47–48% 量的其实就是这个量化。
MSAA 之后边缘变成覆盖率斜坡，再用硬阈值去读，等于把亚像素信息重新量化掉：最外侧那个 alpha 刚过 8
的半覆盖像素会随亚像素移动忽隐忽现，每次都记成跳一格，于是**指标恰好在抗锯齿起作用的地方惩罚它**。
B 臂原口径 56.50% 比 A 臂还差，就是这么来的。

替代口径也不是随便选的。第一版试的是"第一个 alpha≥128 的像素，减去它上面那个像素的 alpha 占比"，
**这个是错的**：色标带电平驱动的 alpha 淡出，轮廓下面压着一整条渐隐带，A 臂有 83% 的列在实心像素上方
存在半透明像素，而那是电平不是覆盖率。最终用的是**从顶部累积 alpha、取累积量跨过一个像素不透明度的
位置并线性插值**——软淡出和 MSAA 斜坡在这个定义下是同一件事，硬边缘则退化回整数位置，两臂可比。

**测量时必须关掉 Grid。** 地板线是静态几何，会在地形根本没覆盖的列里被当成轮廓，每一列贡献一个
必然为零的样本，把百分比稀释掉；关掉 Grid 同时也去掉了画在同一张画布上的轴标签。

#### 素材：正弦不能用

`capture-rig.mjs` 的 `synthesizeSignal` 合成的是纯正弦，对这个指标是废的——一根窄脊，几乎没有轮廓。
这次用的是合成的宽谱素材（粉噪底 + 八个各自慢速扫频的分音 + 约 3 Hz 的瞬态），−19.8 LUFS，
真峰 −1.36 dBTP，零削顶（削顶会产生宽带谐波，直接污染高频地形）。

**它的有效性有一个外部校验点，而且过了**：A 臂在这段素材上量到 48.88%，落在本文件早先记录的
47–48% 带内。素材和探针都复现了当初那次测量。

#### 夹具：三个坑

**`Get-Process plvs` 匹配不到 `plvs-armB-measure`。** PowerShell 的进程名匹配不带通配，
所以"杀掉上一臂"这一步静默失效，最多时三个实例同时活着抢同一个 9222 端口，而只有一个能绑上——
**此后每一个读数都不知道来自哪个进程**。中间一整段数据因此作废。杀进程必须用
`Where-Object { $_.ProcessName -like 'plvs*' }`，并且在启动下一臂后断言只剩一个。

**窗口尺寸逐次启动不一样。** 同一套配置，三次启动分别拿到 1383×640、1918×886、2222×1026 的画布。
点数和行上限都跟画布走（`pointCountFor(W)`、`surfaceRowCap`），像素差 2.6 倍，成本读数就不可比。
**每条成本读数都要连画布尺寸一起记。**

**采集设备不跨启动持久化。** 面板控制项（Grid、Colorize、Mode）会持久化，设备选择不会，
每次启动退回配置里的那一个。有一整臂因此对着没有信号的设备采了 2 分半的静音，
面板全空——正是 `protocol.md` §10.3 那个陷阱的另一个版本。测量前必须读状态栏确认设备。

### `--disable-gpu` 下 WebGL Surface 实际可用（2026-09-01，修正测量）

上一版“画不出来”的结论是**测量错误**。生产 canvas 明确使用
`preserveDrawingBuffer: false`；在 WebGL 绘制回调之外调用 `readPixels`，缓冲内容本来就是未定义的，
连续读到同一份旧内容不能推出用户看到的合成画面冻结。合成负载因为把 `readPixels` 当同步屏障放在 draw
内而能更新，真实 Surface 的旧探针却在 draw 外读，两者从一开始就不是同一把尺子。

新增 `npm run diagnose:surface-fallback`：以 `--disable-gpu` 启动真实 Heavy preset 和 VB-Cable，
在 `drawElements` 处只记录 GL 状态，不读取 drawing buffer；是否可见、是否在更新改由 CDP 对整页**合成后
截图**，裁出 Spectrogram 区域后比较两张相隔 3 秒的图。这量的是用户最终看到的画面，不依赖
`preserveDrawingBuffer`。

15 秒实测：

| 检查 | 结果 |
| --- | ---: |
| renderer | Microsoft Basic Render Driver / D3D11（WARP） |
| 真实 Surface `drawElements` | `888` 次 |
| GL error / context lost | `0 / false` |
| 顶点位置 / VAO / 顶点与索引 buffer | `0 / 已绑定 / 已绑定` |
| 两张合成截图中的变化 | `614 / 198,633` px（`0.309%`） |
| UI 丢帧 / 音频丢块 | `0 / 0` |

截图中地形清晰可见，并在 3 秒间继续向前填充；同一诊断的前一轮是 `640` px（`0.322%`），结果一致。
**结论恢复为：软件 WebGL 回退可用，不需要为这个假象新增 CPU Surface 分支。** `--disable-gpu` 仍只是
人为最坏情况代理；这项验收回答兼容性，不把它当真实无独显机器的性能分布。

## 2. 已落地：滚动复用（2026-08-29）

实时窗口只是向前走时，把已画的图整体左移，只重画新进来的那一条。

| | 改前 | 改后 | 占预算 |
| --- | --- | --- | --- |
| 600×300 | 5.50 ms | **0.050 ms** | 34% → **0.3%** |
| 1200×600 | 19.33 ms | **0.203 ms** | **121% → 1.3%** |

大面板从**超出帧预算**变成 1.3%。

### 为什么可以这么做，以及它凭什么不出错

图像的最左列代表的时刻由 `paintedOldestMs` 记着，**不等于**窗口真正的 `oldestMs`——两者允许
相差不到一列。`spectrogramScrollPlan` 每帧算出该滑几个整像素，并把新的原点**返回**而不是从窗口
重新推导，所以那点零头永远被记着、永远不累积。测试里跑一万帧之后仍然断言滞后 < 1 列。

60 秒窗口铺在 600 像素上，一行 40 ms 只占 **0.4 像素**——所以多数帧根本不该移动。这类帧只重画
最右一列（一行数据会先落进那一列，才慢慢挣到属于自己的一列），代价可忽略。

### 安全边界写成了"只有时间在动"

`slidable` 的判定是正向白名单：实时模式、非冻结、同一个 view、span 与 sampleMs 未变、窗口只向前。
**任何一条不满足就整幅重绘。** 写成"只有时间在动"而不是"以下情况需要失效"，是为了让以后新增的
控件默认走不进滚动路径，而不是悄悄留下一张过期的图。

缩放、平移、改 dB Floor / Tilt / 主题色阶、改尺寸或频率范围、拖动回放——全部落回原路径。

### 保证正确性的那个测试

`sliding versus repainting` 连续滑 200 帧，然后拿同一时刻**从零重绘**的图逐字节比对，必须完全
相同。另有一个用例专门验证时间轴上的真实空隙不会被滑过去的旧像素糊住。

写这个测试时它一开始就红了——查出来是我夹具里 `timestampAt` 越界（`spectrogramFrameEndMs` 会
读 index+1），不是实现的问题。这正是这类等价测试的价值：它逼着人分清"实现错了"和"测试错了"。

## 3. 原始待决策记录（已解决，保留推理过程）

真正的修法是**别重绘没变的部分**：把已有图像整体左移，只画新进来的那一列。稳态成本从
5.7 / 20.1 ms 降到 0.008 / 0.016 ms 量级。

但它把重绘语义从"无状态"改成"有状态"，要处理的情况不止一种：

- **窗口每帧前进的像素数不是整数**（1500 行落在 600 像素上，每行 0.4 px），整数化的滚动会累积漂移
- **缩放、平移、改窗口长度**都会让 x↔时间的映射整体改变，必须全量重绘
- **改 dB Floor、tilt、主题色阶**会改变每个像素，必须全量重绘
- **画布尺寸变化**同上
- **快照/拖动回放**模式下窗口是冻结的，不滚动
- **时间轴上的真实空隙**当前是靠"不画"来表达透明，滚动复用时要保证空隙不会被旧像素填上

每一条都有对应的失效模式，且都是视觉上很显眼的那种（拖影、错位、空隙被糊住）。这是一次真正的
设计改动，不是局部优化，所以停在这里等决策。

## 3.5 滚动路径实际有没有被走到（2026-08-29，实测）

滚动复用做完之后，profile 里 `paintSpan` 仍然排第一（4.2%）。这个问号只能靠计数回答，
所以给两条路径各加了一个计数器，并把应用自带的面板 CPU 计数器改成**发布构建里也挂上**——
渲染性能采样跑的就是发布构建，只在开发构建里暴露等于把仪器锁在了它唯一有用的场合之外。
（计数默认关闭，要显式打开。）

### 结果：文件分析模式下一次都没走到，原因是窗口长度每帧都在变

第一次测：8 秒 256 次绘制，**256 次全是整幅重绘**。

于是查条件。发现两处我写错的地方：

1. **`sampleMs` 不该进判定。** 它是"最后两行的间隔"，随调度抖动，逐帧相等是不可能满足的。
   而它只影响**最右一列**和空隙边缘（`spectrogramFrameEndMs` 对其余行取下一行的时间戳），
   最右一列本来就每帧重画。已移出。
2. **`span` 也不该要求精确相等。** 窗口两端是历史时间戳，长度天然有毫秒抖动。改成**按像素判**：
   只要图像的映射与实时映射相差不到半列，图就还是对的图。而且是拿"图当初绘制时的 span"
   做基准而不是上一帧的，这样缓慢漂移也不会累积过半列。

改完再测，仍然 353/353 整幅重绘。加上"被哪个条件挡住"的计数后，答案是
**`spanChanged`，353/353**——文件分析模式下窗口长度每帧的变化**真的**超过半列。

这不是抖动，是真的变了：文件分析按批推进，一帧内窗口滑过很多行，而那些行的时间间隔并不均匀。
对这种情况，整幅重绘是**正确的选择**——滑动会把像素放错位置。

### 所以现状是

- 滚动复用的**正确性**有测试保证（200 帧滚动后与从零重绘逐字节相同）。
- 它在**文件分析模式下不生效**，而且不该生效。
- 当时在**实时采集下是否生效无法验证**——远程会话里拿不到音频设备，唯一能产生帧的途径就是
  文件分析。后来 capture rig 已经打通，实测结果见 §3.6。

最坏情况它是惰性的（退回改动前的行为），最好情况是 100 倍。要确认，在本机会话里开着实时采集
跑一条命令即可：

```js
const p = window.__PLVS_PANEL_CPU__;
p.reset(); p.enable();
setTimeout(() => { p.disable(); console.table(p.snapshot()); }, 8000);
```

看 `spectrogram2d:slidStrip` 与 `spectrogram2d:fullRepaint` 的比例；若仍被挡住，
`spectrogram2d:noSlide:<原因>` 会直接说是哪一条。

## 3.6 实时滚动路径已验证（2026-08-31）

Windows WebView2、VB-Cable + VLC 实时信号，同一真实窗口计 10 秒：

| 事件 | 次数 |
| --- | ---: |
| scheduled / callback | 197 / 197 |
| signature skip | 23 |
| **实际绘制（dirty paint）** | **174** |
| **slid strip** | **160** |
| full repaint | 14 |
| `noSlide:spanChanged` | 14 |

**160 / 174 = 92.0% 的脏帧走滚动条带。** 剩余 14 次全图重画都有明确的 `spanChanged` 原因，
是完整 paint signature 的正确性回退，不是优化失效。此前文件分析 353/353 全图重画与这次 Live
160/174 滚动并不矛盾：前者一批跨过多行、窗口映射每帧真变；后者按实时节奏前进，绝大多数帧只需
滑动已有像素再补右侧新条带。这一项关闭。
