# PLVS 0.22.0 release readiness

Date: 2026-10-18
Baseline release: 0.21.0
Candidate release: 0.22.0

## Purpose

Keep the remaining work for the first stable Linux release explicit while Linux package integration
and final Windows release validation happen on different machines. This is a working release record,
not publication approval. The repository remains at version 0.21.0 until the candidate is complete.

## Work that must land before the release candidate

- Integrate the published `ffmpeg-sidecar-7.1.5-r1` Linux x86_64 FFmpeg and FFprobe assets into the
  application fetcher and the stable deb's private resource layout. Do not resolve them through
  `/usr/bin`.
- Add an immutable ADR that supersedes ADR 0032 for the stable package while leaving the current
  Preview decision historically intact.
- Add a stable-identity Ubuntu 24.04 x86_64 deb builder. Preserve the Preview identity, isolated
  state, disabled updater, and package conflict instead of converting Preview in place.
- Prove on a clean Ubuntu 24.04 system that the exact deb installs, owns the expected application,
  CLI, sidecar, manifest, desktop, and license files, resolves only allowed shared libraries,
  analyzes representative files, launches, persists state, and removes cleanly.
- Add the stable deb, updater signature, `linux-x86_64-deb` manifest descriptor, evidence artifact,
  and exact asset name to the release workflow and bundle validator. Keep in-app Linux installation
  disabled until the separate upgrade-acceptance conditions in the Linux stable update audit are
  satisfied.
- Update the release skill and contributing guide only after the commands and artifact contracts
  exist and are tested.

## Windows release-machine work

The range since 0.21.0 changes `src-tauri/src/audio/`, `dsp`, and `engine`, so the capture gate is in
scope even if the final commits are release plumbing or documentation.

1. Synchronize the exact candidate on a clean Windows checkout and fetch the pinned sidecars.
2. Verify `device-enumeration` in `plvs-cli doctor --json`, then run `npm run smoke:capture` with the
   VB-Cable and VLC rig. A rig error or missing loudness result is not a product pass and has no
   release bypass.
3. Run `npm run soak:capture` for the default four hours. Compare drift with the recomputed spread
   of complete runs in `artifacts/soak/`, not only with the script's absolute 0.01 dB limit.
4. Run the Windows packaged-update acceptance flow for the exact candidate SHA and retain its
   report. Recheck updater recovery, settings retention, and multi-workbench restoration if any
   update-runtime code changes after the evidence run.

## Final candidate content

Complete these only after the Linux implementation and platform evidence are merged:

- Choose and apply version 0.22.0 through the repository version command, then verify all three
  version owners agree.
- Generate the changelog from conventional commits and review every user-visible change rather
  than treating commit grouping as editorial approval.
- Reconcile `docs/user/`, the README, website homepage, and screenshots. Current public guidance
  describes Linux as Preview-only and stable Linux as unavailable; it must not be changed before
  the stable package contract is true.
- Review the full data-handling range. The current privacy record explicitly requires final
  confirmation of updater behavior and the policy's 2026-10-16 effective-date decision before
  publication.
- Only after the candidate commit is otherwise final, run `npm run release:content:snapshot`,
  complete `docs/release-content-review.json`, run its check, and commit the record. Any later
  tracked change invalidates that fingerprint and requires a fresh review.

## Publication gates

1. Run `npm run release:preflight` from a clean checkout. This must exercise the capture smoke
   because capture dependencies changed.
2. Push the exact candidate SHA and wait for its full CI run to pass.
3. Confirm remote `main` still equals the reviewed SHA, verify GitHub immutable Releases support,
   and dispatch the stable release workflow. Do not create the product tag manually.
4. Verify the Draft contains every Windows, macOS, and Linux asset, updater signature, manifest,
   license resource, and required evidence before the irreversible publish step.
5. After publication, verify the immutable Release, updater manifest, downloads, and independent
   website deployment from their exact SHAs.

## Evidence already available

- Version ownership is internally consistent at 0.21.0.
- Sharesets compatibility minima are registered.
- `ffmpeg-sidecar-7.1.5-r1` is published as an immutable tooling release with Linux, macOS, and
  Windows binaries plus complete corresponding source.

These facts are prerequisites only. They are not evidence for the not-yet-created 0.22.0 candidate.

## Deliberately deferred

- Linux package installation, native desktop, capture, and updater testing require the Linux
  machine.
- Windows capture smoke, four-hour soak, and packaged-update acceptance require the Windows rig.
- Version bump, final content-review fingerprint, release dispatch, and website publication must
  target the final reviewed SHA and therefore cannot be completed early.
